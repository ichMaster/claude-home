# t1129 — the Sent-log trim corrupts records containing U+2028/U+2029/NEL

## Problem / goal

`json.dumps(..., ensure_ascii=False)` does not escape U+2028 LINE SEPARATOR, U+2029
PARAGRAPH SEPARATOR or U+0085 NEL, so a message containing one (text copied from the web is
the usual source) is appended as one valid JSONL line. The trim in
`status/tools/sent_log.py append()` then reads the file with `.splitlines()` — which splits
on those characters too — and rejoins with `\n`, permanently turning that record into two
unparseable lines. The panel's Sent screen shows «не розібрано» for it forever, and the line
cap counts fragments. The trim fires whenever the log passes `sent.max_lines` (5000), which
is guaranteed with timers sending every 2–15 minutes.

## Test cases

- **TC1 (regression) —** a record whose text contains U+2028 survives a trim pass: the file
  still holds one valid JSON line per record, and `json.loads` succeeds on each (fails
  before the change).
- **TC2 —** the trim still caps the file at `max_lines` records, counting records rather
  than visual lines.
- **TC3 — edge:** U+2029 and NEL behave the same as U+2028.

## Approach

Trim by splitting on `"\n"` only — the one separator the appender writes — instead of
`.splitlines()`, dropping the trailing empty element. The dump is left as is: escaping the
characters would change what the panel shows, and the boundary is the real invariant.
