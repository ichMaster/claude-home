# t1128 — notify.sh exits 0 on a failed delivery (t1046 regression via t1121)

## Problem / goal

Before t1121, a curl transport failure aborted `notify.sh` under `set -e` with a non-zero
exit. `status/watch.py` relies on exactly that (t1046): it persists its "already reported"
signature only when `notify.sh` returns 0, because recording an undelivered send silences
that alert forever. The t1121 rewrite wrapped every curl in `set +e` so the Sent log could
record the failure — correct — but then the script runs to its end and exits 0 on every
outcome. With Telegram unreachable (routine here during outages), a changed warn signature
is persisted as "sent" and that notification is lost for good.

## Test cases

- **TC1 (regression) —** `--no-voice` with a stubbed curl transport failure → non-zero exit
  (fails before the change: exits 0).
- **TC2 —** `--no-voice` with a stubbed HTTP 400 → non-zero exit (not delivered either).
- **TC3 —** text delivered, voice call fails → exit 0: the alert reached the chat, and
  `watch.py` must not re-send it.
- **TC4 —** `--voice-only` with a failed synthesis → non-zero exit (nothing was delivered).
- **TC5 —** the ok path stays 0, and the Sent log still gets exactly one record in every
  case above (t1121 must not regress back).

## Approach

A `finish` helper at every exit point: write the Sent log (as now), then exit 1 when the
message did not reach the chat — for a text-bearing call that means `text_code != 200`;
for `--voice-only`, `voice_code != 200`. An empty text (no part attempted) keeps exit 0,
matching the pre-t1121 contract. All callers checked: every Python caller uses
`check=False`, no shell caller runs under `set -e`, and `watch.py` is the one that wants
the code.
