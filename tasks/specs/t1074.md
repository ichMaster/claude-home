# t1074 — admin panel, phase 6: the Tasks screen

Phase 6 of `t1037` (`docs/features/ADMIN-PANEL.md`, screen 9). Phase 5 (Prompt and
Scenarios) is deferred at the owner's request, 2026-10-31.

## Problem / goal

The task list is a chat message. Twenty-three open tasks arrive as text, and every change
— closing one, moving a date, starting the clock — is a sentence that has to be typed and
parsed. That works while he is walking; it is the wrong instrument while he is looking at
the list and deciding what today actually holds.

## What it is

Four columns over the same append-only log the session reads:

- **Сьогодні** — overdue and due today, overdue first and marked;
- **Період** — tasks with a period (a weekend, a week) and no hard date;
- **Беклог** — no date and no period;
- **Закриті** — what was closed or cancelled recently, so a day's work is visible.

Each card shows the title, project, estimate, the real time spent if the clock has run,
the 📌 if a block was asked for, and its calendar events with their times.

Buttons per task: **закрити**, **почав** / **зупинив**, **на сьогодні** / **на завтра** /
**на вихідні**, and **📌** to toggle the block request. A box at the top adds a task — the
same `store.py add` the Telegram command uses, so the date in the text is parsed by the
same code.

## What this screen deliberately does not do

- **No drag and drop.** The design says "drag to change a date"; that needs a client
  framework the design also forbids, and three buttons do the same job on a page that has
  to work on a machine with no internet. Written here so the deviation is a decision, not
  a gap.
- **No event deletion.** Unlinking removes the link in the task log; the event itself
  lives in Google Calendar, which only the connector can touch. The screen says so where
  it would otherwise look like a delete that silently half-worked.
- **No estimates, no planning.** Choosing when a block goes is the planning problem, and
  it needs the outage schedule and the sleep window. Out of scope.

## Test cases

- **TC1 — columns.** `columns()` puts an overdue task and one due today in «Сьогодні»
  (overdue first and flagged), a task with a period in «Період», a bare one in «Беклог»,
  and a closed one in «Закриті»; a task that is both overdue and has a period counts once,
  in «Сьогодні», because the date is the stronger claim.
- **TC2 — what a card shows.** `card()` reports spent minutes from the run log, marks a
  running task, carries the estimate and the block flag, and lists plan events separately
  from fact events.
- **TC3 — actions call the store, not the file.** Each button runs `store.py` with the
  right verb and id; an unknown action changes nothing and says so.
- **TC4 — adding.** The add box runs `store.py add` with the text as one argument, so the
  date inside it is parsed by the same code the Telegram command uses. An empty box is
  refused without running anything.
- **TC5 — the token.** Every form carries it and a POST without it is refused, as on
  `/zirka`.
- **TC6 — escaping.** A task title is free text the owner typed and is escaped; so is a
  project name.

## Approach

`panel/tasks_screen.py` for the column logic, pure over a `state()` dict so the tests
never touch the real log. Writes go through `store.py` as a subprocess — the log stays
append-only and its validation stays in one place.
