# t1167 — remind.py marks a nudge sent even when notify.sh failed

## Problem / goal

`notify()` runs notify.sh with `capture_output=True` and discards the return code; the state
key (`<event>:lead` / `<event>:checkin`) is recorded unconditionally right after. notify.sh
exits 1 when the text part was not delivered (its `finish()` is the delivery verdict). So a
Telegram outage during the one `window_min`-wide slot loses that nudge forever — the key says
"sent", and the window has passed by the next tick. watch.py was fixed for exactly this class
in t1046 («state is persisted only after a delivered send»); remind.py was not.

Found by the nightly code review, 2026-11-12 (scan report, Medium #10).

## Test cases

- **TC1 —** given an event inside the lead window and notify.sh exiting 1, when `main()`
  runs, then the `:lead` key is NOT recorded, so the next tick retries (regression: fails
  before the fix).
- **TC2 —** same event with notify.sh exiting 0 → the key IS recorded (delivery still
  deduplicates).

## Approach

`notify()` returns `returncode == 0`; both call sites record the key only on a truthful
return. At worst a nudge repeats once within the window, which t1050 already accepts.
