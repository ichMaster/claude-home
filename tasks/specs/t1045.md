# t1045 — mail probe: no IMAP timeout; >60 new mails silently skipped forever

## Problem / goal

1. **No timeout.** `imaplib.IMAP4_SSL("imap.gmail.com", 993)` uses a blocking socket with no
   deadline — the only network probe without one (cal, loe, alarm, weather, news all set it).
   A blackholed connection mid-fetch hangs the probe, `status/run.sh`, and whatever invoked
   it (the digest, `/mail`).
2. **Overflow loss.** Only the newest 60 UIDs are fetched (`uids[-60:]`), but `last_uid`
   advances to the max of ALL found UIDs. After a burst or days offline, everything older
   than the newest 60 is permanently skipped — never shown, never fetched again, including
   mail matching the `важливе` rules — and the headline says «60 нових» with no hint.

## Test cases

- **TC1 (regression)** — `pick_batch` with 100 UIDs and cap 60 returns the oldest 60, a
  `last_uid` equal to the highest fetched UID, and remaining=40; filtering the original list
  by `> last_uid` yields exactly the 40 skipped ones (they are found on the next run).
- **TC2 (regression)** — the IMAP connection is opened with a `timeout` kwarg (captured via a
  fake `IMAP4_SSL`).
- **TC3** — `pick_batch` with fewer UIDs than the cap returns them all and remaining=0.

## Approach

`IMAP4_SSL(..., timeout=conf("probes.mail.timeout", 25))`. Process the oldest `cap` UIDs
first and persist `last_uid` as the max of the fetched batch only, so the remainder is picked
up next run; the headline states the overflow («і ще N — наступного разу»). Batch cap moves
to `probes.mail.batch` (60). Script body wrapped in `main()` for testability. The Low
findings on this file (unguarded state read, non-atomic write) stay as reported.
