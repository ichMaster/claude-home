# t1205 — a rebooked block never nudges again

## Problem / goal

`status/remind.py` keys its sent-state by event id alone (`<event>:lead`,
`<event>:checkin`), and entries live two days. The documented replan flow — the owner
answers «не за планом», the session moves the block with the connector's `update_event`
(the Google event keeps its id) and re-links it with the new start — produces a moved block
whose keys are already recorded: no heads-up at the new time, no check-in. The exact flow
the check-in exists to trigger yields a block that arrives unannounced. Nothing clears the
keys on unlink either. Found by the nightly review of 2026-11-18 (Medium).

## Test cases

- **TC1 — regression:** state holds the nudge keys for the block's **old** start; the event
  now carries a new start inside the lead window → the lead nudge fires (fails before the
  change: the id-only key is already present and the nudge is skipped).
- **TC2 —** the same event at the same start stays deduplicated — one send, recorded, not
  re-sent on the next tick (the existing t1167 contract, re-keyed).
- **TC3 —** a recorded nudge for the same start is not re-sent (the existing t1050/t1167
  tests, moved to the new key format).

## Approach

The key includes the start the nudge is about: `nudge_key(event, start, kind)` →
`<event>:<start>:lead|checkin`, one helper used by both call sites and by the tests. Old
id-only entries in `reminders.json` simply age out through the existing two-day window; no
migration. Clearing keys on `unlink` was considered and dropped — the log lives in
`tasks/store.py`, which knows nothing of reminder state, and the start-scoped key already
covers the move. Out of scope: nudging about a block whose *task* changed while the time
stayed.
