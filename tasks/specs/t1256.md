# t1256 — digest/social/youtube units get TimeoutStartSec

## Problem / goal

`noos-digest.service`, `noos-social.service` and `noos-youtube.service` are
Type=oneshot with no `TimeoutStartSec`, and for oneshot systemd defaults it to
**infinity** (verified live: `systemctl --user show` reported
TimeoutStartUSec=infinity for exactly these three). Each wraps a headless `claude -p`
run that can wedge on network or MCP. While the unit stays `activating`, the timer's
next elapses are no-ops — so a single hung 08:03 digest kills the 20:03 digest and
every one after it, with no message anywhere. Every other claude-p unit already
carries the bound (noos-mood2 1800, noos-bio 900, noos-bots 900, noos-codereview 3600,
noos-subs 300); these three were missed.

## Test cases

- **TC1 —** every `noos-*.service` in `~/.config/systemd/user/` whose ExecStart wraps
  a headless `claude -p` script carries a `TimeoutStartSec` line (regression: fails
  for the three units before the fix). The test skips cleanly on a machine without
  the unit directory, so the public suite stays green elsewhere.
- **TC2 — live:** after `daemon-reload`, `systemctl --user show` reports a finite
  TimeoutStartUSec for all three (verified by hand, recorded in the fix report — a
  test must not shell out to systemctl).

## Approach

Add `TimeoutStartSec=1800` to noos-digest.service and `TimeoutStartSec=900` to
noos-social.service and noos-youtube.service — the bounds matching their siblings
(digest is the longest run, like mood2's 1800). `systemctl --user daemon-reload`.
The units live outside the repo; the test is the repo-side guard.
