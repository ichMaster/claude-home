# t1202 — notify.sh delivers any unrecognized dash-token as the message text

## Problem / goal

The flag loop in `notify.sh` ends with `*) break ;;` and then `text="$*"`: there is no
`--help` handling and no unknown-flag guard. A caller probing usage — which the headless
digest model demonstrably does — gets the literal flag stamped, synthesized and delivered:
`chat-log.jsonl` records voiced «--help» messages on 2026-11-03, 11-06, 11-13 and 11-14,
each with text and voice both 200. A typo'd flag (`--voicetext "spoken" "body"`) is mangled
into the message the same way instead of failing loudly. Found by the nightly review of
2026-11-18 (Medium).

A message legitimately starting with a single dash («-5 градусів надворі») must keep
working — only `--`-style tokens are flags here.

## Test cases

- **TC1 — regression:** `notify.sh --help` prints the usage header and exits 0 without
  calling the Telegram API at all (fails before the change: «--help» is sent as a message).
- **TC2 — regression:** `notify.sh --bogus "привіт"` exits 2 with an error on stderr and
  nothing is sent (fails before: «--bogus привіт» is delivered as one message).
- **TC3 — edge:** a message starting with a single dash («-5 градусів…») still goes out as
  text — the guard must not over-block.
- **TC4 — edge:** `notify.sh -- "--literal"` sends the literal text after the `--`
  separator, the standard escape hatch.

Tests run against a fake `$HOME` with a stub `curl` on `PATH` and a fake `.env.telegram`,
so nothing real is ever sent even while the test is red.

## Approach

Three new cases in the existing flag loop, before the final `*) break`: `--help|-h` prints
the header comment and exits 0; `--` is the end-of-flags separator; any other `--*` token
is refused with exit 2. Single-dash tokens still fall through to the text, as today.
Out of scope: validating flag *values* (an empty `--bot ""` etc. keeps its current
fallback behaviour).
