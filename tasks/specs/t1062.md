# t1062 — admin panel, phase 2: the Changes and review screen

Phase 2 of `t1037` (`docs/features/ADMIN-PANEL.md`, screen 10).

## Problem / goal

The development process says: no change without a task, no task without a spec and tests,
every commit naming its task id, a security reading of every staged diff, a nightly
self-review that fixes High and Medium. All of that happens and none of it is *visible* —
the verdicts are spoken once into a chat and scroll away, and the only way to ask "what was
built today and how was it checked" is to read `git log` beside two directories by hand.

One gap has to be closed before the screen can exist: **the commit-time security reading is
not recorded anywhere.** It is performed and then lost. A screen that showed nothing in that
column would read as "no problem found" when the truth is "nobody wrote it down".

## What it is

- **Commits**, newest first: hash, date, subject, the task id taken from the message, the
  files touched, and whether the commit is still local or already on the public remote. A
  commit with no task id is flagged — the process says there should not be one.
- **Behind each commit**: the task's title and state, its spec with the test cases, and the
  test files that name the same id.
- **The security reading** for that commit, from `status/state/commit-review/<sha>.md`, with
  "не записано" said plainly where there is none rather than left blank.
- **The nightly reviews**: the scan and fix reports per night, with counts by severity.
- **The standing Low list**: Low findings are reported and never fixed, so they pile up
  across nights where nobody sees the pile. Deduplicated, oldest first, with the night each
  was first raised.
- **Push state**: how many commits are ahead of `origin/main`.
- **The change log** in full, with a search box and a filter by kind.

## Test cases

- **TC1 — commits.** `commit_rows()` parses the log into hash, date, subject and task id;
  a message with no `(t####)` is marked `no_task`; commits ahead of the remote are marked
  local. Parsing is over a fixed captured `git log` string, so the test needs no repository.
- **TC2 — what is behind a commit.** Given a task id, the row carries the spec path when
  `tasks/specs/<id>.md` exists, the test files naming that id, and `None` where they do not
  exist. A missing spec is reported, never invented.
- **TC3 — the security reading.** Present when `status/state/commit-review/<sha>.md` exists,
  and explicitly absent otherwise — the two must not look the same.
- **TC4 — reviews.** `review_nights()` pairs a scan with its fix report by date, counts
  findings per severity from the scan's headings, and survives a report whose shape it does
  not recognise by reporting it raw rather than raising.
- **TC5 — the Low list.** `open_lows()` collects Low findings across nights, deduplicates by
  title, and keeps the earliest night each appeared.
- **TC6 — rendering and routing.** `/changes` renders, every interpolated value is escaped
  (a commit subject and a change-log command line are both attacker-reachable in principle
  and arbitrary in practice), and the search box filters the change log without a reload
  loop.

## Approach

`panel/changes.py` holds the collectors, pure over text passed in wherever possible: the
git calls live in one thin function and the parsing is tested against captured output.

The reports are our own generated Markdown, so reading their `## Severity` / `### Title`
headings is reading a format we control, not parsing someone's prose — and anything
unrecognised is shown raw instead of being guessed at.

Separately, and outside the panel: the commit-time review starts being written to
`status/state/commit-review/<sha>.md` (git-ignored, like the nightly reports). The habit
has to exist before the column has anything to show.

Out of scope: triggering anything from this screen. Phase 2 is read-only like phase 1 —
no re-running a review, no pushing, no closing a finding. Those are actions, and actions
come after the panel has proved it reads correctly.
