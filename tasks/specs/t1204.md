# t1204 — a torn mood.json silently consumes every message to Zirka

## Problem / goal

`status/mood.py` writes `status/state/mood.json` with a bare `write_text` in `save_state`
and `save_bio_state` (truncate, then write), against the repo's own atomic-write rule —
and `noos-bio.timer` rewrites the file daily at 08:20, on a host where power cuts are
routine. `zirka_context()` in `status/bots/inbox.py` then parses it with an unguarded
`json.loads` — unlike `bruno_context()` right below, which guards both of its reads. A torn
file raises `JSONDecodeError`, which `handle_update`'s catch swallows **after** the offset
was committed: every message to Zirka — calibration feedback, forwarded references — is
consumed with no reply, no retry and no notice, until the next successful mood run (~24 h).
Found by the nightly review of 2026-11-18 (Medium).

## Test cases

- **TC1 — regression:** `zirka_context()` over a truncated `mood.json` returns the same
  fallback as a missing file instead of raising (fails before the change:
  `json.JSONDecodeError` escapes).
- **TC2 —** `save_state` and `save_bio_state` go through `atomic_write_text`, the same
  helper every other state writer uses — so the torn file can no longer be produced by a
  kill mid-write (fails before: both use a bare `write_text`).
- **TC3 — edge:** a valid `mood.json` still renders the forecast and biorhythm fields
  exactly as before.

## Approach

Guard the read (`try/except OSError, json.JSONDecodeError` → the existing missing-file
fallback) and switch the two writers to `atomic_write_text`, which `mood.py` already
imports. Both ends are fixed because either alone leaves the other half of the failure:
a guard without atomicity still loses the day's reading; atomicity without a guard still
dies on a file torn by anything else. Out of scope: the offset-commit-before-reply order
in `inbox.py` (a design trade-off — a crashing update must not wedge the queue).
