# t1166 — double start on a running task leaves an open run forever

## Problem / goal

`state()` replays `op == "start"` with an unconditional append of `{"from": ts, "to": None}`,
while `stop` (and `done`, which appends one `stop`) closes only `runs[-1]`. A repeated
`/doing` on an already-running task — a double-tapped Telegram command — leaves the first run
with `to: None` forever: `minutes()` computes `now - from` for it on every read, so `spent`,
`similar` and the ⏱ marker report ever-growing fact time for a closed task, corrupting the
plan-vs-fact data estimates are built from. The log is append-only, so the damage cannot be
repaired by any later event.

Found by the nightly code review, 2026-11-12 (scan report, Medium #9).

## Test cases

- **TC1 —** given a task with `start`, `start`, `done` in the log, when `state()` replays it,
  then no run is left open and the fact time stays bounded (regression: fails before the fix
  with one run open forever).
- **TC2 —** a normal `start` → `stop` → `start` → `stop` sequence still yields two closed
  runs (the guard must not merge genuinely separate runs).

## Approach

In the `start` replay branch: when the last run is still open, the second `start` is a no-op
(the task is already running). This heals existing corrupted histories on replay too, since
state is always rebuilt from the log. No change to `stop`/`done`.
