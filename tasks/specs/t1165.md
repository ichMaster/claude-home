# t1165 — restart-session.sh ignores a failed handoff and reports a stale note

## Problem / goal

The `--summary` path runs `handoff.py` with its exit code unchecked (and handoff.py can die
on an uncaught `TimeoutExpired`), then touches `.fresh` regardless — so a failed note means
the next session starts with an empty context AND no note: the thread is simply lost. Worse,
the success report measures `memory/handoff-last.md`, which on that path still holds the
note of a *previous* restart, so Telegram says «Записка: N символів» about a stale file and
the loss is invisible.

Found by the nightly code review, 2026-11-12 (scan report, Medium #8).

## Test cases

- **TC1 —** given handoff.py exiting non-zero and a stale `handoff-last.md` on disk, when
  `restart-session.sh --summary` runs (with stubbed notify/systemctl/pgrep/sleep), then
  `.fresh` is NOT created (the conversation is kept, as `--continue` would) and the report
  says the note failed instead of quoting the stale size (regression: fails before the fix).
- **TC2 —** handoff.py succeeding → `.fresh` is created and the report carries the fresh
  note's own size, measured from `memory/handoff.md`.

## Approach

Check handoff.py's exit code and that `memory/handoff.md` is non-empty; measure the size
right there, before start.sh moves the file. On failure, fall back to the existing
`--continue` behaviour (`rm -f .fresh`) — keeping the conversation is the only way not to
lose the thread when the note could not be written — and say so in the report. No change to
`--continue` / `--fresh` modes.
