# t1185 — a voice message lost to a transcription failure gets a visible reply

## Problem / goal

`transcribe()` returns "" whenever `dg_stt.sh` exits non-zero (Deepgram 5xx, network down,
curl timeout), and a subprocess timeout raises and is caught by poll()'s per-update guard.
In both cases the offset is already saved, the update lands only in dropped.jsonl, and the
owner — who speaks rather than types — gets no reply and no error anywhere: the message is
permanently lost even when the outage lasts one timer tick. He has no way to know he was not
heard.

## Test cases

- **TC1 — regression:** a voice update whose transcription returns "" produces one reply in
  the bot's own chat saying the voice was not recognised and asking to repeat, and a
  dropped.jsonl record saying «голос не розпізнано» (fails before: silence, record says
  «без тексту»).
- **TC2:** a transcription that **raises** (timeout) produces the same visible reply instead
  of only the generic «збій обробки» drop.
- **TC3 — edge:** a plain empty message (no voice) still drops silently as «без тексту» —
  no notice spam for stickers/photos; and a dry run sends nothing.

## Approach

Catch transcription failure inside `handle_update` (exception → same as empty), and when a
voice message ends with no text, send a short fixed notice through the bot's own `send()` —
counted against the hourly cap so a long Deepgram outage cannot spam — and log the drop as
«голос не розпізнано». Retrying by holding the offset back was considered and rejected: the
offset is deliberately committed per update (t1041/t1089), and a retry loop against a dead
Deepgram would re-pay the download every two minutes; a visible ask-to-repeat matches how
the owner actually uses the bots.
