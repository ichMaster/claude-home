# t1089 — bot inbox state is persisted only after the whole batch

## Problem / goal

Nightly review 2026-11-01. `status/bots/inbox.py poll()` saves state once, after the loop.
`noos-bots.service` is `Type=oneshot` with `TimeoutStartSec=900` and no signal handling;
one heavy Bruno chain (intent + search + answer + handover) carries up to ~870 s of
subprocess timeouts, so a backlog of a few such messages can outlive 900 s and be
SIGKILLed **after** replies went out but **before** `save_state()`. The offset never
advances, the answers list (hourly cap) is lost, and every two-minute timer tick replays
the same batch — duplicate replies, duplicate mood-feedback records poisoning calibration,
burned quota — until Telegram expires the unconfirmed updates (~24 h). The t1041 fix covers
exceptions inside the loop, not a kill.

## Test cases

- **TC1 —** two text updates; handling of the second dies with `KeyboardInterrupt` (an
  uncatchable-by-the-loop stand-in for a kill). The state file on disk already holds
  `offset == first_update_id + 1`, so a rerun replays at most the message that was mid-
  flight — never the already-answered one (regression — fails before the change: no state
  file is written at all).
- **TC2 —** a `--dry-run` still saves nothing, even per update (the 2026-10-30 rule: a dry
  run must not consume the queue).
- **TC3 — edge:** the happy path still answers everything and ends with the offset past the
  last update (the existing t1041 tests keep passing).

## Approach

Persist inside the loop: after each update is handled (answered or logged-and-skipped),
`save_state` unless dry-run. The final save goes away — nothing mutates state after the
loop. A kill can still land between `send()` and the save, so at most one message can
replay; bounding it to one is the point, eliminating it would need an outbox redesign that
is out of scope.
