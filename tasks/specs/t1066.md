# t1066 — panel: the change-log search matches hidden fields and covers half a day

Fix from the phase-2 review (`status/state/code-review/2026-10-31-panel-phase2-scan.md`,
M4 and M5 — one task, same code path).

## Problem / goal

Two failures in the `/changes` search:

1. The filter tests `needle in json.dumps(r)` over the **whole** record, including `cwd`
   (always `/home/ich/claude-home`), `session` (a hex uuid) and the JSON keys. Searching
   «ich», «home», «claude» or «kind» matches every record — verified live, `q=ich`
   returned a full page.
2. The query filters only the newest `panel.changes_full` (200) records, while
   2026-10-31 alone holds 484 changelog lines — the spec's «журнал змін у повному обсязі з
   пошуком» actually searches less than half of today. A miss renders «Сьогодні записів
   немає», indistinguishable from "no such change was ever made".

## Test cases

- **TC1 (regression)** — a record whose `cwd`/`session` contain the needle but whose
  rendered fields (`ts`, `kind`, `target`, `detail`) do not, does NOT match; a needle in
  `target` or `detail` does, case-insensitively. Fails before.
- **TC2 (regression)** — with a query set and nothing matching, the page says the search
  found nothing («нічого не знайдено»), not «Сьогодні записів немає»; without a query the
  empty state stays as it was. Fails before.
- **TC3** — a search reads `panel.changes_search` records (config, default 5000), not
  `panel.changes_full`; without a query the old limit stands.

## Approach

A pure `filter_changes(rows, query)` in `panel/changes.py` matching only the four fields
the table renders, used by `changes_html`; the search path asks `recent_changes` for
`panel.changes_search` (new config key, 5000 — covers weeks at the current rate) and the
display cap of 60 stays. `render_changes` keys the empty-state message on the query.
Out of scope: the filter-by-kind dropdown from the design doc (a feature, not this fix).
