# t1172 — a failed Telegram delivery of the morning reading is detected and reported

## Problem / goal

`notify.sh` deliberately exits non-zero when Telegram answers non-200 — «the exit code is the
delivery verdict» (t1121) — but `mood.send()` runs both notify calls with `check=False` and
never looks at the returncode. The 08:15 v2 reading (`mood2.py --send` delivers through this
same sender) and the 08:20 biorhythms can therefore fail to arrive while the timer shows
success, the state carries `sent_at`, and `mood2.report_failure` — built for exactly «the
reading just never arrives, with no sign why» (t1160) — is never invoked.

Found by the nightly code review of 2026-11-13 (Medium, confirmed adversarially).

## Test cases

- **TC1 —** `mood.send()` returns `False` when notify.sh exits non-zero and `True` when both
  calls exit 0 (regression — before the fix it returns None either way).
- **TC2 —** `mood2.send()` raises `Undelivered` when `mood.send` reports failure.
- **TC3 —** `mood2.main --send` with a failing delivery returns a non-zero exit code and
  calls `report_failure` with a message that says the reading was built but not delivered.

## Approach

`mood.send()` keeps `check=False` but inspects both returncodes, prints the failure to stderr
and returns a bool. `mood.main()` folds the send results into its exit code (0 only when all
sends landed). `mood2.send()` raises a new `Undelivered` on a False return; `mood2.main`
catches it beside the other failure classes, reports through `report_failure` and returns 5.
report_failure itself still never raises — if Telegram is down entirely, the exit code is the
remaining record.
