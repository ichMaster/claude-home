# t1130 — bot state written non-atomically; a torn write re-answers the last batch

## Problem / goal

`status/bots/inbox.py save_state()` writes `status/state/bots/<bot>.json` with a plain
`write_text` after every handled update. The code's own comment at poll() names the kill
scenario (the oneshot service SIGKILLed past TimeoutStartSec mid-backlog); a power cut —
routine on this machine — does the same. A kill landing mid-write truncates the file;
`load_state()` catches the JSONDecodeError and falls back to `{"offset": 0, ...}`, so the
next run calls `getUpdates` with offset 0, re-fetches the still-unconfirmed batch and
re-answers messages already answered (duplicate replies in the owner's chat, duplicate
feedback records), and the hourly anti-flood counter and conversation history are wiped.
`watch.py`, `remind.py` and `sent_log.py` already use `noosconf.atomic_write_text` for
exactly this reason.

## Test cases

- **TC1 (regression) —** `save_state` writes through a temp-file + rename: a crash
  simulated at the moment of the write never leaves the state file torn — the file on disk
  is always either the old state or the new one, both valid JSON.
- **TC2 —** a normal save round-trips: `load_state` returns what was saved, history capped
  as before.

## Approach

Import `atomic_write_text` from `noosconf` and use it in `save_state()` — the same one-line
pattern the other state writers use. TC1 asserts the mechanism (no plain `write_text`, temp
+ `os.replace`) by interposing on the file operations, which is the honest way to test
atomicity without actually killing a process mid-syscall.
