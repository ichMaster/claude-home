# t1249 — inbox send() checks notify.sh's exit code

## Problem / goal

`status/bots/inbox.py` `send()` runs notify.sh with `check=False` and never reads
the return code, although notify.sh's exit code is designed to be the delivery
verdict (non-zero on a Telegram failure or a rejected argument, t1202). On the main
answer path `handle_update` commits the bot's history entry and charges the hourly
cap **before** calling send, and the offset is committed by the caller regardless —
so a transient Telegram failure silently consumes the owner's message: no
dropped.jsonl record, no retry, no notice. This is the same loss class
t1185/t1213/t1227 closed on the voice, document and model-call legs, left open on
the delivery leg. (Nightly review 2026-11-23, Medium, verified.)

## Test cases

- **TC1 (regression) —** given send() returning failure, when handle_update answers
  an owner message, then it returns 0, «доставка не вдалася» is appended to
  dropped.jsonl, the bot's unsaid reply is not committed to history and the hourly
  cap is not charged. Fails before the change.
- **TC2 —** send() itself: a notify.sh exiting non-zero → False; exiting 0 → True.
- **TC3 —** a successful send still commits history and the cap (existing tests).

## Approach

`send()` returns `proc.returncode == 0`. On the main path the user's words stay in
history (he did speak), but the reply-commit, the cap charge and the success print
happen only after a true send; a false one is logged to dropped.jsonl and the
update counts as unanswered. The apology legs keep ignoring the result — they are
already inside loss-reporting paths. The offset stays committed (retrying against a
dead Telegram every two minutes was rejected in t1185's design); the loss is now
recorded instead of invisible.
