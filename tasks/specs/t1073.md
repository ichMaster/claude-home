# t1073 — panel: valid-JSON-non-object input takes the Bruno screen down

Found by the phase-4 review (`status/state/code-review/2026-10-31-panel-phase4-scan.md`,
M1). Fixes collectors added in t1072.

## Problem

`topics()` catches only `json.JSONDecodeError`, so a topic file holding `null`, `[]` or a
bare string — valid JSON, not an object — raises `AttributeError` on `t.get(...)` and
`/bruno` answers 500: the whole screen is down, while TC6 of t1072 promises a malformed
topic file costs one row, not the screen. The same hole sits in `_lines()`: a torn JSONL
line whose surviving fragment parses as a scalar (`123` is valid JSON) flows into
`r.get(...)` in `archive_stats()`, `archive_search()`, `dropped_news()` and
`bruno_chat()` and 500s the screen the same way — TC3/TC4 promise a torn line is
survived, but only the *invalid*-JSON kind is. A `джерела` value that is not a list of
strings breaks the render too (`TypeError` on join, or a string joined into characters).

`sent_news()` in the same commit catches `AttributeError` for exactly this case, so the
hazard was known — these spots missed it.

## Fix

- `_lines()` keeps only dicts.
- `topics()` reports a non-dict document as a broken row («не обʼєкт»), and coerces
  `джерела` to a list of strings.

## Test cases

- **TC1** — a topic file containing `null` (and one containing `[1, 2]`) yields a row
  with `broken` set; the good file beside it still parses; nothing raises.
- **TC2** — a topic file with `"джерела": "nature.com"` and one with `"джерела": [42]`
  render through `_topics_table` without raising and without character-split garbage.
- **TC3** — a JSONL line that is a valid JSON scalar (`123`) is skipped by `_lines`
  consumers: `dropped_news()` and `archive_stats()` return as if the line were torn.
