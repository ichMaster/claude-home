# t1140 — record the astro forecast as-is, then build a parallel v2

## Problem / goal

The owner's verdict on 2026-11-08: «та все ми не вірно зробили, це не працює. Давай зараз
запишемо все як є і зробимо паралельну версію». The current forecast (v1) is not what he
needs, but *what* to replace it with is not settled yet. Three iterations have already been
spent and partly forgotten — atmosphere, then event prediction, then checkable states — so
the first requirement is a record, not a rewrite.

Two deliverables:

1. **An as-is record** of v1 — the computed facts, the three-call pipeline, every prompt, the
   state files, the shape rules, the calibration loop, and the dead ends with the reason each
   was abandoned. `docs/concept-mood.md` is stale (it still describes the seventeen-call
   pipeline removed in t1126), so the record is a new document and the stale one is retired.
2. **A parallel v2** that can be developed and run without touching v1: its own entry point,
   its own prompt directory, its own log and state, nothing on a timer. Both versions run on
   the same day so the readings can be compared side by side.

v1 keeps running at 08:15 until the owner says v2 replaces it.

## Test cases

- **TC1 —** `status/mood2.py --dry-run` runs the v2 pipeline and sends nothing, writes
  nothing to v1's log (`status/state/mood.log`) or v1's state (`status/state/mood.json`).
- **TC2 —** v2 writes only to its own paths: `astro2.log`, `astro2.state`,
  `astro2.claims` resolve under `status/state/` with `v2` in the name, and a v2 run leaves
  every v1 state file byte-identical.
- **TC3 —** v2 reads its prompts from `status/mood2/`; a missing prompt is a clear error
  naming the file, not a silent empty prompt.
- **TC4 —** the facts handed to v2 come from the same `status/astro.py` as v1 (one ephemeris,
  not two), verified by comparing the fact lines of both for one fixed date.
- **TC5 — edge:** with no `astro2` block in config, v2 refuses to run rather than falling
  back to v1's paths — a silent fallback would let v2 write into v1's history.
- **TC6 —** the as-is document names every v1 prompt file that exists in `status/mood/`, so
  the record cannot quietly go out of date on a prompt that was never mentioned.

## Approach

The record first, because it does not depend on what v2 turns out to be. Then the v2 scaffold
— entry point, prompt directory, config block, state paths — with the prompts left as
placeholders until the owner says what a reading should be. Content comes in a separate task.

Deliberately out of scope: changing v1 in any way, changing timers, deciding the v2 reading's
shape.
