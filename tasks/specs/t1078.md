# t1078 — the task board must not re-fire an action on refresh

Found by the phase-6 review (04c09b7, finding M2 in
`status/state/code-review/2026-10-31-panel-phase6-scan.md`).

## Problem

A POST to `/tasks` answers 200 with the re-rendered page, so the browser's current page *is*
the form submission: reload it (or walk back and forward) and the browser re-submits.
A re-fired `add` appends a duplicate task; a re-fired `start` opens a second parallel run
that `minutes()` double-counts. The log is append-only by design — neither can be cleaned
up afterwards.

## Fix

Post/Redirect/Get: the POST runs the action, then answers `303 See Other` to
`/tasks?m=<result>`; the GET renders the board with the message from the query. After the
redirect the page in the browser is a plain GET — refresh re-reads, never re-writes.

The message in the URL is display-only, length-capped and escaped like any other text;
`/zirka` keeps its old shape for now (L1 in the scan — its re-fires do not corrupt the
task log, and phase 3 is reviewed code this phase did not touch).

## Test cases

- **TC1** — over real HTTP: a valid POST to `/tasks` answers 303 with
  `Location: /tasks?m=…`, not 200. (Fails before the fix: 200.)
- **TC2** — following the Location with GET shows the action's message on the board.
- **TC3** — a POST without the token is still refused with 403 and performs nothing.
