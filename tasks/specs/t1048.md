# t1048 — parse_due crashes on version-like numbers; defer with no parseable date wipes the deadline

## Problem / goal

1. The dotted-date pattern in `parse_due` (`tasks/store.py`) matches any `d.m` pair and calls
   `date(y, mo, d)` with no range check: `add "оновити python 3.14"` crashes with
   `ValueError: month must be in 1..12` (reproduced live while opening this very task),
   `add "звіт до 31.11"` crashes with day-out-of-range. The task is not created and `/task`
   from Telegram dies.
2. `defer <id> "<phrase>"` with a phrase `parse_due` cannot read (e.g. «пʼятниця» without the
   preposition the weekday pattern requires) appends `due: null` — the existing deadline is
   silently cleared and the task drops out of the overdue/today probe.

## Test cases

- **TC1 (regression)** — `parse_due("оновити python 3.14")` and `parse_due("звіт до 31.11")`
  do not raise; the impossible date is treated as not-a-date (title keeps the number, due is
  None or from another pattern).
- **TC2 (regression)** — `defer` with an unparseable date phrase exits with an error and does
  not append a `defer` event, keeping the existing due date.
- **TC3** — a valid `defer <id> завтра` still works.

## Approach

Wrap the `date()` construction in the dotted-date branch in try/except `ValueError` and fall
through to the remaining patterns. In the `defer` command, when the date argument is
non-empty but `parse_due` returns None, print an error and exit 1 instead of appending
`due: null`. Deliberately NOT changing which phrases parse (e.g. a bare weekday) — that is
owner-tuned behaviour; only the crash and the silent wipe.
