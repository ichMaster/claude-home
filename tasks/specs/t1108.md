# t1108 — the panel's HTTP surface: a negative length, no deadline, a bypassable lock

Found by the full review, 2026-11-01 (security H1, H3, M2, M3, M4 in
`status/state/code-review/2026-11-01-panel-full-security.md`).

## Problem

Five findings, one surface — the part of the panel that answers before anyone is logged in.

- **H1, memory.** `min(int(Content-Length), cap)` returns the header when it is negative, and
  `rfile.read(-1)` reads until the client stops. One unauthenticated `POST /login` with
  `Content-Length: -1` took the **live** panel from 24 MiB to 85 MiB, and a private instance
  to 3.8 GiB in six seconds. The unit has no `MemoryMax`.
- **H3, the lock.** The attempt counter was read and written without a lock, so a burst from
  one address verified **43 of 60** passwords inside a window that allows five — and the
  correct password at slot 60 still got a session cookie. The rate limit was decoration
  against anything but a sequential guesser.
- **M2, the disk.** One log line per attempt, on an endpoint that needs no session: 5.9 GiB
  a day measured at 1035 requests a second, on a disk with 13.7 GiB free.
- **M3, the threads.** A connection that sent headers and then nothing parked a server
  thread for ever; 200 of them stayed alive. No deadline existed anywhere.
- **M4, `clear`.** `auth.py clear` prints that the panel now lets nobody in, and every live
  session kept working for its full twelve hours: `valid_session` never asked whether a
  password was still configured.

## Fix

- `body_length()` clamps to `[0, panel.max_post_bytes]` — no negative, no unbounded read.
- One `threading.Lock` around the whole login check, so counting and verifying happen
  together. Logins queue; for one person logging in once a day that costs nothing.
- One log line per lockout instead of per attempt, with the flag cleared on success.
- `Handler.timeout = 30`, which `BaseHTTPRequestHandler` applies to the socket.
- `valid_session()` returns False when no password is configured, so `clear` closes the open
  sessions as it claims to.

## Test cases

- **TC1 —** `body_length` is never negative and never above the cap, for a negative header, a
  huge one, a missing one and a non-numeric one. (Fails before: the negative passes through.)
- **TC2 —** thirty-one concurrent attempts from one address let at most one through, and the
  address is locked afterwards. (Fails before: many verify.)
- **TC3 —** 500 attempts from one address leave fewer than twenty log lines, one of them a
  lockout. (Fails before: 500 lines.)
- **TC4 —** `Handler.timeout` is a positive number.
- **TC5 —** clearing the password invalidates a live session. (Fails before: it stays valid.)
