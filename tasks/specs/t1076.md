# t1076 — one writer at a time for the task log

Found by the phase-6 review (04c09b7, finding M3 in
`status/state/code-review/2026-10-31-panel-phase6-scan.md`).

## Problem

`next_id()` is a read-modify-write over `tasks/tasks.jsonl` with no lock: two `store.py add`
processes that overlap both read the log before either appends, both mint the same id, and
`state()` replay keeps only the second — the first task's line stays in the log but the task
is invisible everywhere (list, digest, reminders, the board). Demonstrated by interleaving
two writers: both got `t001`, one title vanished.

Until phase 6 the session was effectively the only writer; the panel is now a second
always-on one (and the nightly review a third), so the overlap is no longer theoretical —
a double-click on «додати» is two concurrent adds.

## Fix

An exclusive `flock` on `tasks/.lock`, taken in `main()` before the state read for every
mutating command (add, done, cancel, defer, edit, block, start, stop, link, unlink, md) and
held until the process exits. Read-only commands (list, spent, similar, events) take
nothing, so a hung writer can never block the probes. Blocking lock: operations take
milliseconds, and the panel's subprocess timeout is the backstop.

## Test cases

- **TC1** — while another process holds the writer lock, `add` waits; it completes (and the
  task exists) once the lock is released. (Fails before the fix: add sails through.)
- **TC2** — `list` ignores the writer lock and answers while it is held.
