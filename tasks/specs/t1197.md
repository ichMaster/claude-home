# t1197 — an empty wide extraction must not be cached for the month

## Problem / goal

`wide_entries()` (status/mood2.py) caches whatever the `wide` stage returned, keyed by the
hash of his month+year texts. When the model once answers wrong — the array wrapped in an
object (`{"entries": [...]}`), a bare `[]`, or a list of strings — the filter yields
`entries=[]` and that empty list is written to the cache unconditionally. The texts do not
change through the month, so the hash matches every later morning: `[]` comes back from the
cache with no model call and no note. One transient model flake silently removes the
month/year horizon from every reading until his next forward. Found by the nightly review
of 2026-11-17 (Medium).

## Test cases

- **TC1 — regression:** given the `wide` stage answering `{"entries": [...]}` (the array
  wrapped in an object, a common model deviation), `wide_entries()` returns those entries
  instead of an empty list.
- **TC2 — regression:** given a first call answering `[]` and a second call answering real
  entries, the second `wide_entries()` run calls the model again (the empty result was not
  served from cache) and returns the entries.
- **TC3 —** a non-empty extraction is still cached: two runs over the same texts cost one
  model call (the existing `test_the_extraction_is_cached_by_the_text` keeps passing).

## Approach

Two smallest changes in `wide_entries()`: unwrap a dict answer whose `entries` key holds a
list before filtering, and skip the cache write when the filtered list is empty — an empty
answer is retried on the next run rather than remembered for the month. A genuinely empty
month would cost one extra call per morning, which his texts make practically impossible and
which is the right price for never going silently blind. Out of scope: --dry-run writing the
cache (reported as Low, not fixed here).
