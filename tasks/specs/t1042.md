# t1042 — voice scripts: curl without --max-time hangs every timer that speaks

## Problem / goal

`voice/el_say.sh` (ElevenLabs TTS), `voice/dg_stt.sh` (Deepgram STT) and `voice/el_stt.sh`
(Scribe STT) call `curl` with no `-m/--max-time` and no `--connect-timeout`. `notify.sh`
voices by default and is called from `remind.py` and `watch.py` via `subprocess.run` with no
timeout; `noos-remind`/`noos-watch`/`noos-changes` are `Type=oneshot` with no
`TimeoutStartSec` (default infinity for oneshot). A TLS connection to the API that stalls
after connect blocks curl forever → the unit stays `activating` → the timer never fires
again. All reminders and watch alerts stop until manual intervention. `notify.sh`'s own
Telegram curls already carry `-m`, which is the house convention.

## Test cases

- **TC1 (regression)** — every `curl` invocation in `voice/el_say.sh`, `voice/dg_stt.sh`,
  `voice/el_stt.sh` carries a `--max-time`/`-m` bound. Fails before the change, passes after.
- **TC2** — the edited scripts still parse (`bash -n`).

## Approach

Add `--connect-timeout 10 --max-time 120` to the three curl calls — generous enough for a
minute of synthesized audio or a long voice note upload, bounded enough that a stall fails
within two minutes and the oneshot unit completes. No unit-file changes (out of scope — those
live outside the repo).
