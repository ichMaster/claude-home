# t1212 — Scribe error JSON is printed as the transcript

## Problem / goal

`voice/el_stt.sh` prints `d.get("text") or json.dumps(d)[:400]` to stdout and exits 0.
When ElevenLabs answers with an error body (bad key, quota, unsupported format), the raw
error JSON goes out on stdout as if it were the recognized text. `dg_stt.sh` execs this
script whenever Deepgram returns an empty transcript (short clips — the reason the
fallback exists), and `inbox.py`'s `transcribe()` returns stdout unchecked — so during an
ElevenLabs outage every short voice message silently becomes a JSON blob answered as the
owner's words, and the same path feeds the main session's recognition. The `or` also
means a legitimately empty transcript (silence) prints the whole response JSON instead of
an empty string. Found by the nightly self-review of 2026-11-19 (Medium).

## Test cases

All run the real script with `HOME` pointed at a temp dir (dummy `.env.voice`) and a
stubbed `curl` on PATH, so nothing leaves the machine.

- **TC1 —** given curl answering an error JSON (no `text` key), the script prints the
  error to stderr and exits non-zero; stdout is empty. (regression — fails before the
  change: the JSON lands on stdout with exit 0)
- **TC2 —** given a response with `"text": ""` (recognized silence), stdout is empty and
  the exit code is 0 — an empty transcript is an answer, not an error.
- **TC3 — edge:** a normal `"text": "привіт"` response still prints `привіт`, exit 0.

## Approach

The inline python mirrors dg_stt.sh's own contract: `"text" in d` → print it (even
empty); otherwise the body goes to stderr and the script exits 1, which dg_stt.sh's
caller already treats as a failed recognition.
