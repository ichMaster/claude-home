# t1049 — ingest.py: --rebuild corrupts the FTS index; stat-size offsets lose or duplicate records

## Problem / goal

1. **Rebuild order.** `fts` is `content='chunks'` (external content). `--rebuild` runs
   `DELETE FROM files; DELETE FROM chunks; DELETE FROM fts;` — by the time fts rows are
   deleted the content rows are gone, so FTS5 cannot remove the old tokens. Reproduced in
   sqlite3: after this order plus a re-insert, `MATCH` returns the rowid of an unrelated new
   chunk and the FTS5 integrity check reports a malformed index. Every `--rebuild` poisons
   `search.sh` results.
2. **Offset = stat size.** `size = f.stat().st_size` is taken before reading, the loop then
   consumes to EOF, and `bytes=size` is recorded. Transcripts grow while the live session
   writes: a tail torn mid-write fails `json.loads`, is skipped, and the next run seeks past
   its start — the record is permanently unindexed. Lines appended between stat and EOF are
   indexed now and re-read next run — duplicate chunks.

## Test cases

- **TC1 (regression)** — schema + one indexed chunk; `clear_all`; insert a new chunk; `MATCH`
  on the old term returns nothing, `MATCH` on the new term returns the new rowid, and
  `INSERT INTO fts(fts) VALUES('integrity-check')` passes.
- **TC2 (regression)** — a file with one complete line and one torn line: `tail_lines`
  returns only the complete line, with the offset pointing before the torn one; after the
  torn line is completed on disk, reading from that offset returns the completed record (no
  loss, no duplicate).
- **TC3** — reading again from the returned offset with no new data returns nothing.

## Approach

Rebuild uses FTS5's documented `delete-all` command before clearing `chunks`/`files`.
Incremental reads go through `tail_lines()`: binary readline, offset advanced only past
lines ending in `\n`, recorded offset = position actually consumed. No behaviour change for
complete files.
