# t1209 — news seen-set trimmed by hash order re-reports recent stories

## Problem / goal

`status/probes/news.py` stores seen stories as 12-hex sha1 prefixes and trims the state
with `sorted(seen)[-800:]` — the lexicographically largest 800 survive. Hashes are random,
so once a topic crosses 800 keys (current files hold ~260 after a month; roughly two
months away), every write evicts an arbitrary set of keys *including ones added in that
very run*: a story whose hash sorts low is forgotten immediately, passes the `key in
seen` check on the next hourly poll, and is re-reported as fresh — repeatedly. This is
the exact defect class already fixed in `youtube.py` (`trim_seen`, t1044), whose
docstring names it. Found by the nightly self-review of 2026-11-19 (Medium).

## Test cases

- **TC1 —** given a seen file already holding 800 keys that all sort above the new
  story's hash, when the probe runs twice (second run reading the state the first one
  wrote), then the second run reports «нічого нового» — the fresh key survived the trim.
  (regression — fails before the change: the story is re-reported)
- **TC2 —** given a seen file over the cap, when the probe writes state, then the oldest
  entries are evicted and the file stays at 800. (recency, not sort order)
- **TC3 — edge:** the existing t1170 suite still passes — a torn file still yields an
  empty seen set and a valid rewrite.

## Approach

Keep the stored state as an insertion-ordered list (it already is a JSON list): load it
into both a list (order) and a set (membership), append fresh keys to the list, and write
`list[-800:]` without sorting — newest-by-insertion survive, same contract as youtube's
`trim_seen`. Existing state files lose their (meaningless, sorted) order once; from then
on order is recency.
