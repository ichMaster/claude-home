# t1121 — the Sent log did not record the one failure it exists for

Found by the phase-9 review (79a0d25, H1 and M1-M5 in
`status/state/code-review/2026-11-01-panel-phase9-scan.md`).

## Problems and fixes

**H1 — a transport failure left no record, and took a delivered message with it.** Both sends
capture the code as `code=$(curl … -w '%{http_code}')`, and under `set -euo pipefail` that
assignment *is* the command: a curl that cannot connect — timeout, DNS, TLS, every case where
Telegram is unreachable rather than refusing — aborted the script before `sent_log` ran.
`voice/el_say.sh` is the same shape and exits 1 on any non-200 from ElevenLabs, including a
drained quota on an account this project documents as shared. So the most likely failure of
all was the one the log could not show — and when the text part had already gone out and the
voice call failed, the whole record vanished, delivered half included.

Now: each send runs with `set +e`, its exit status becomes code `0` plus an `error` field, and
`sent_log` is called from an `EXIT` trap as well as from the normal path, guarded so it writes
exactly once. A synthesis failure records the text part's real code and says why.

**M1 — the kind fallback is dead for the four senders that matter most.** `caller()` reads the
process tree, which cannot work where the caller is a model: `noos-digest`,
`noos-youtube`, `noos-social` and `noos-codereview` send through `claude -p`, whose child is a
harness shell. The four wrappers now export `NOOS_SENT_KIND`, `notify.sh` honours it, and
`--kind` still wins. The docstring's claim about «the session says `claude`» is gone — it
returned `""`.

**M2 — `bot` named the bot that was asked for.** On the token fallback (a named bot with no
`TELEGRAM_BOT_TOKEN_<SUFFIX>` in a hand-maintained file) the message goes to the main chat and
the record said otherwise — while the chat id is deliberately absent *because* that field was
supposed to say where the message went. It now records the bot used, plus `asked` when they
differ, and the screen shows both.

**M3 — concurrent appends lost records at the cap.** The trim is a read-modify-write and
several timers fire together; 11 to 15 of 20 records vanished, including the line the writer
had just committed. The append and the trim are now one `flock`ed section.

**M4 — filter links were HTML-escaped but not URL-encoded**, so a kind containing `&`, `+` or
`#` made the screen's own link answer «ще нічого» about a record that is there.

**M5 — the wiring was tested by grepping `notify.sh` for two substrings**, `caller()` was
monkeypatched away, and the counters were checked off-screen; H1, M1 and M2 all sat in that
gap. The suite now runs the real `notify.sh` in a temporary `HOME` with a `curl` shim and
stubs for `el_say.sh`/`to_ogg.py`, and asserts the record for: a 400, a transport failure, a
delivered text with a failed voice call, a refused synthesis, and the happy path producing
exactly one record.

Low findings fixed in passing, all of them about the screen stating what it does not know: a
record with no `ok` printed a literal «200»; `chars` and the `codes` keys skipped escaping; a
record of the wrong shape downed the whole screen; the header passed the whole log's counters
off as the filtered view; and the log file was created 0664 although it holds the text of
every message sent — now 600.
