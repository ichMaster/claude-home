# t1131 — claims_file() ignores --subject: a subject run deletes the owner's claims

## Problem / goal

Every other state file is per subject through `state_path()` (`mood-kira.log`,
`mood-kira.json`), but `claims_file()` always returns the shared
`status/state/forecast-claims.jsonl`. `save_claims()` replaces all rows of the same day
before writing, so running `mood.py --subject kira` on a day the owner's 08:15 forecast
already ran **deletes the owner's claims for that day** and writes Кіра's in their place.
At 21:00 `noos-mood-ask` then builds the evening question from those — asking the owner, in
his chat, whether Кіра's predicted states happened — and `mood_feedback.score()` is polluted
the same way.

## Test cases

- **TC1 (regression) —** with `astro.SUBJECT` set, `claims_file()` returns a per-subject
  path (`forecast-claims-kira.jsonl`), not the owner's file (fails before the change).
- **TC2 —** save the owner's claims, then save a subject's claims for the same day: the
  owner's rows are untouched and `load_claims(day)` for the owner still returns them.
- **TC3 —** the explicit `CLAIMS` override (tests use it) still wins.

## Approach

Apply the same suffix rule `state_path()` uses, in `claims_file()` itself — one place, no
caller changes. Calibration already refuses to run for subjects; the claims follow the same
isolation («one chart never writes into another's history»).
