# t1060 — Moon aspects are read at noon, so half the day's triggers never exist

## Problem

`day_sky()` reads the sky once, at local noon, "because the Moon moves 13° a day, so noon
is the fair midpoint". That is fair for *where the Moon is*. It is wrong for *what the Moon
does*: an aspect it forms in the evening is simply absent from the facts, and no later
stage can recover what was never computed.

Caught against a real reference on 2026-10-31. The astrologer's hourly calendar carries
`☽27°♋ ☐ ♀27°♎` from 20:29 — the Moon squaring retrograde Venus in the owner's 8th house.
At noon the Moon is at 19° Cancer, 7° from that square and outside the 5° orb, so our run
produced nothing at all for the whole evening. Three of the reference's four factors matched
ours to the degree; the fourth was missing for this reason alone.

The loss is systematic, not a one-off: the Moon covers about 13° a day, more than twice the
widest orb here, so **every Moon aspect whose exactness falls outside a few hours around
noon is invisible to us** — roughly half of them, and they are precisely the sharp, dated
triggers a day is actually made of.

## Test cases

- **TC1 (regression)** — for 2026-10-31, `moon_events()` includes a square from the Moon to
  Venus, exact in the evening (local hour ≥ 18), with Venus named. The current code produces
  no such fact. The ephemeris is deterministic and offline, so this is a fixed-date test with
  no stubbing.
- **TC2** — the same call still reports the Moon–Mercury trine that the noon snapshot does
  find, so nothing already working is lost.
- **TC3** — each event carries the hour it is exact and the window it holds, and the window
  is bounded by the day: a Moon aspect must never be reported as lasting weeks.
- **TC4** — aspects to the natal chart are covered as well as aspects in the sky: a transit
  of the Moon to a natal point that is exact in the evening appears.
- **TC5** — events are deduplicated by (target, aspect): one entry per pairing per day, at
  its tightest moment, not one per sampling step.

## Approach

`moon_events(day, step_hours)` walks the day in steps (default 2 h, which cannot miss a
passage since the Moon moves ~1.1° in that time against a 5–6° orb), computes the Moon's
aspects to the nine other bodies and to the natal points at each step, and keeps for each
pairing the step where the orb is tightest. Around that step it refines to the nearest
ten minutes, so the reported hour is usable rather than a two-hour bucket.

Each event becomes a fact with `layer: "moon"` whose text names the time —
«транзитний Місяць квадратура Венера, точно близько 20:30» — so the Moon layer's call sees
the day as a sequence rather than a single frame. The noon positions stay exactly as they
are: this adds facts, it does not change any existing one.

Cost: ~12 extra `calc_ut` calls per body per day, which is microseconds — no model is
involved, so nothing here costs a call.

Out of scope: hourly windows in the reading itself. The owner said plainly (2026-10-31) that
hour-by-hour windows are too fine for him and readings stay daily; the time is there so the
story can say "ближче до вечора", not so it can print a timetable.
