# t1176 — a large forwarded document no longer kills the bot reply via the argv limit

## Problem / goal

`read_document()` accepts documents up to `telegram.inbox.max_document_bytes` (262144), but
the body is appended to the message and passed as a **single argv element** to `claude -p`
(call_claude) and to `mood_feedback.py` (record_feedback). Linux caps one exec argument at
MAX_ARG_STRLEN = 131072 bytes, so a forwarded ~150 KB .txt makes every model call raise
OSError [Errno 7]; the exception lands in poll's per-update except after the offset was
already advanced and saved — the owner's message is consumed with no reply, ever. The config
explicitly permits a size the pipeline can never process.

Found by the nightly code review of 2026-11-13 (Medium; the E2BIG was verified by execution
on this host).

## Test cases

- **TC1 —** a 150 KB text document is read and clamped so its UTF-8 size fits an argv
  element with room for the prompt around it, ending with an explicit truncation marker
  (regression — before the fix the full body is returned).
- **TC2 —** a document inside the budget passes through untouched, no marker.
- **TC3 — edge:** the clamp cuts cleanly inside a multi-byte Cyrillic character (decode with
  `ignore`, no exception, valid text).

## Approach

Clamp the decoded text in `read_document()` to `telegram.inbox.max_document_prompt_bytes`
(new config key, default 98304 — 96 KB, leaving ~32 KB of the 128 KB argv element for the
prompt template and history) and append «…(документ обрізано, далі не влізло)». Most of a
reference still arrives and gets a reply instead of the whole message silently vanishing.
Switching the claude call to stdin was considered and set aside: argv is also the path to
mood_feedback.py and astro_learn, and one clamp covers them all with far less surface.
