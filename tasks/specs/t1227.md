# t1227 — a failed answering call says the loss in the chat

## Problem / goal

`status/bots/inbox.py` `handle_update`: when `answer()` raises (the model call fails —
API outage, 5xx, the 180 s timeout, expired login beyond the fallback token), the
`except` only prints to the journal and returns 0. The offset was already committed by
`poll()`, so the owner's message is consumed forever: no reply in the chat, no
`dropped.jsonl` record — the bot simply appears to ignore him. Every sibling failure
path in the same function was explicitly fixed to say the loss out loud: voice (t1185),
document download (t1213), document refusal (t1218). This branch was missed.

## Test cases

- **TC1 —** given `answer` raising RuntimeError, `handle_update` sends a loss notice to
  the bot's chat and logs the update to dropped.jsonl (regression; fails before the
  fix).
- **TC2 —** the notice counts against the hourly cap (an `answers` timestamp is
  appended), so a model outage cannot flood the chat past `max_per_hour`.
- **TC3 — edge:** with the hourly cap already exhausted, the failure is still logged to
  dropped.jsonl but nothing is sent.

## Approach

Mirror the t1213 document pattern in the `except` around `answer()`: `log_dropped`,
then — within the cap and not in dry-run — append the cap timestamp and `send()` a
short notice («Не вийшло відповісти — спробуй ще раз трохи згодом.»). The offset stays
committed, as everywhere else: retrying against a dead model every two minutes was
already rejected for voice (t1185).
