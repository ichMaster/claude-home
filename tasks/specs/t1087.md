# t1087 — set_pin() writes an unvalidated level; one typo breaks load() for everything

## Problem / goal

Nightly review 2026-11-01. `memory/facts.py set_pin()` substitutes whatever it was handed
into the `pin:` line. Only the panel clamps to 0/1/2 — the CLI passes `sys.argv[3]` raw, so
`facts.py pin <id> high` rewrites the file as `pin: high`. From then on `load()` crashes on
`int('high')` for every command: `list`, `add`, the panel memory screen — and
`facts.py prompt`, whose stderr `start.sh` sends to /dev/null, exits non-zero, so the next
restart assembles the system prompt with zero pinned facts and nothing says why.

## Test cases

- **TC1 —** given a fact file, when `set_pin(p, "high")` is called, then it raises
  `ValueError` and the file is untouched (regression — fails before the change: today it
  writes `pin: high`).
- **TC2 —** `set_pin(p, "7")` — numeric but out of range — is refused the same way.
- **TC3 —** the CLI `pin <id> high` exits non-zero with a message, no traceback, file intact.
- **TC4 — edge:** `set_pin(p, "2")` and `set_pin(p, 0)` still work (the existing t1083 test
  already passes a string).

## Approach

Validate at the function, not the caller: `level = int(level)` and refuse anything outside
0..2 before touching the file. The CLI branch catches `ValueError` and prints a one-line
refusal. The panel's own clamp stays as is.
