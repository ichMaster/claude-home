# t1226 — corrupt mail.json state must not kill the mail probe

## Problem / goal

`status/probes/mail.py` reads its state before the `try:` with no guard:

```python
state = json.loads(STATE.read_text()) if STATE.exists() else {}
last_uid = int(state.get("last_uid", 0))
```

A torn or garbage `status/state/mail.json` (power cut without flush, stray edit) raises
JSONDecodeError (or ValueError on a non-int `last_uid`) on every run, with a traceback
that run.sh discards — so /mail, the digest's mail section and important-mail warns stay
dead until the file is repaired by hand. The project's own standard is the opposite:
youtube.py `load_state` (t1044) and watch.py `load_state` (t1046) tolerate exactly this
input and fall back to a fresh state.

## Test cases

- **TC1 —** given `STATE` containing garbage (`{broken`), `mail.main()` does not raise
  JSONDecodeError — it proceeds to the IMAP step like a fresh install (regression; fails
  before the fix).
- **TC2 —** given `STATE` holding `{"last_uid": "sure"}` (non-int), same: no ValueError,
  fresh-install path.
- **TC3 — edge:** a valid state file still yields its `last_uid` (`load_state` returns
  the stored value).

## Approach

Extract the two lines into a `load_state()` that returns `(state, last_uid)` and treats
any parse failure as `({}, 0)` — identical to the first-run path, which already caps the
backlog by `LOOKBACK_DAYS`. Nothing else changes; the state-before-delivery finding is
separate (reported unfixed, needs a delivery-ack design).
