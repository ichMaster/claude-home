# t1173 — changelog hook logs mutating compound and redirect commands

## Problem / goal

`changelog/hook.py` `classify()` returns None whenever READONLY matches the start of a Bash
command, before the mutating part is considered. So `cat > file <<EOF` (the common heredoc
write idiom), `tail -100 app.log > /tmp/out.txt` and `cat a.txt && rm old.txt` all start with
a read verb, match `^cat`/`^tail`, and are never written to `changelog/YYYY-MM-DD.jsonl` —
the append-only change log (and the 23:30 summary, /changes and the panel's Changes screen
built on it) silently under-reports real filesystem changes. Multi-line commands whose first
line is a read are also lost, because MUTATING's `(^|[;&|]\s*)` anchor does not treat a
newline as a separator.

Found by the nightly code review of 2026-11-13 (Medium, confirmed adversarially).

## Test cases

- **TC1 —** `cat > f <<EOF` classifies as a logged write (regression — None before the fix).
- **TC2 —** `tail -100 a.log > /tmp/out.txt` and `cat a.txt && rm old.txt` classify as logged.
- **TC3 —** a multi-line command whose first line is a read and second line is `rm x`
  classifies as logged.
- **TC4 —** genuinely read-only commands stay unlogged: `cat a.txt`, `git status`,
  `git log --oneline`, `systemctl --user status x`, `sed -n '1p' f`.
- **TC5 —** plain mutating commands keep working: `rm -rf build` logs with verb `rm`.

## Approach

READONLY may only veto what it actually covers: collect all MUTATING matches with
`finditer`, and suppress only when every mutating match starts inside the span READONLY
matched. The verb is taken from the first mutating match beyond the readonly head. A newline
joins the separator class so a second line's verb counts. Known cost: `cat a && git status`
now logs a `git` line — an extra line in a change log is cheaper than a missing `rm`.
