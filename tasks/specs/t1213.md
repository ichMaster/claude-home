# t1213 — a transient getFile error consumes a document with no reply

## Problem / goal

In `status/bots/inbox.py`, `read_document`'s `getFile` call is outside any try — only the
content download below it is wrapped. `handle_update` calls it unguarded, and `poll`
advances the offset before its blanket catch: one network timeout on `getFile` while the
owner forwards an astrologer reference as a `.txt` document means the update is committed
as handled, the exception is logged as «збій обробки», and the document is consumed
forever — no reply, no notice in the chat. The voice path got exactly this notice in
t1185; the document path did not. This re-opens the original 2026-10-31 complaint of
silently lost references. A caption on the failed document is just as bad: the bot would
answer the caption while silently dropping the reference body. Found by the nightly
self-review of 2026-11-19 (Medium).

## Test cases

- **TC1 —** given `api` raising URLError on getFile, when `handle_update` processes an
  owner document message with no caption, then it returns without raising and a notice
  («Документ не прочитався…») is sent to that bot's chat within the hourly cap.
  (regression — fails before the change: the exception propagates)
- **TC2 —** given the same failure on a document carrying a caption, the notice is sent
  and the caption is NOT answered as if the document never existed.
- **TC3 — edge:** a healthy document read is unchanged (existing t1054/t1162 tests).

## Approach

Wrap the `read_document` call in `handle_update` with a try/except that sets a
`doc_failed` flag; on failure, log the drop, send the notice (same cap and answer
accounting as the voice-notice path) and return — the offset stays committed, retrying a
dead network every two minutes was already rejected in t1185. `read_document` itself is
unchanged: the unguarded getFile is now guarded one level up where the notice can be sent.
