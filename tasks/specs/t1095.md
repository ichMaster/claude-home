# t1095 — panel: the interval timers showed «—» for both schedule and next run

Found by the phase-8 review (8c700a3, finding M2, and L7 for the documentation count).

## Problem

t1090 added `_monotonic()` so that the four timers carrying no `OnCalendar` — the watcher,
the bots, the reminders, the transcript indexer — would show their interval. The parser is
correct and **was never wired to systemd**: `rules_html` asks for
`Unit,Description,TimersCalendar,Persistent,NextElapseUSecRealtime,LastTriggerUSec,ActiveState`,
with no `TimersMonotonic`, so `_monotonic()` receives an empty dict on every real run. The
test passed because it fed the property to `schedule_rows` by hand — a parser test standing
in for a wiring test.

So the defect the task claimed to fix was still on the live page, with a green test asserting
otherwise. «—» is not a blank, it is a false claim: it reads as "this timer has no schedule"
about the four timers that run most often.

The «наступний» column is blank for the same four for a related reason: an interval timer
publishes `NextElapseUSecMonotonic` — a span since boot, e.g. `4w 1d 13h 23min 5.346337s` —
not `NextElapseUSecRealtime`.

Separately (L7): the doc and the commit message say "all 15 timers". There are 14 project
timers; the 15th on this machine belongs to another project and is correctly excluded.

## Fix

- `rules_html` requests `TimersMonotonic` and `NextElapseUSecMonotonic`.
- `rules_screen.parse_span()` turns systemd's duration spelling into seconds, and
  `schedule_rows(blobs, boot_epoch=…)` computes the real next-run time for a monotonic timer.
  The clock is injected, so the function stays pure and the test needs no boot.
- The documentation count becomes 14.

## Test cases

- **TC1 —** `rules_html` asks systemd for `TimersMonotonic` and `NextElapseUSecMonotonic`.
  (Fails before the fix: neither is in the property list.)
- **TC2 —** `parse_span` reads `4w 1d 13h 23min 5.346337s`, `15min`, `2min 30s`, `500ms`,
  and returns `None` for nonsense.
- **TC3 —** an interval timer with a monotonic next-elapse and a known boot time renders a
  real date in «наступний»; without a boot time it renders blank rather than a wrong date.
- **TC4 —** a calendar timer is unaffected: its realtime next-elapse still wins.
- **TC5 —** the documentation no longer claims 15 timers.

## Approach

Why not parse `systemctl list-timers`: its columns are formatted for a human and depend on
locale, and the property interface already carries both numbers.
