# t1105 — the config form's reset had none of the save's guards

Found by the full review, 2026-11-01: writes-M1 and security-H2
(`status/state/code-review/2026-11-01-panel-full-writes.md`,
`…-panel-full-security.md`). Two reviewers found it independently; the security one rated it
High because a crafted POST reaches it.

## Problem

`set_setting` refused a masked value, a permission, a list and an unknown key.
`reset_setting` checked only that the key existed in `config.local.json`, then popped it. So:

- `action=reset&key=astro` wiped fourteen leaves — birth data, the written context, the
  second person's chart — in one press;
- `key=probes.youtube.channels` deleted all 603 channels;
- `key=permissions` deleted the whole permission override block, one of the exact two writes
  the design says may never come from a page;
- and «повернуто до типового» was false twice over for those keys: `config.json` carries no
  default for any of them, so the value did not fall back — it ceased to exist.

The button is rendered only on editable rows, so this needed a hand-made POST with a live
form token rather than a click. The asymmetry was still unintended, and
`test_what_the_form_may_not_touch` had no reset counterpart.

## Fix

One function, `_edit_refusal(key)`, answers "may a page write this at all", and **both**
`set_setting` and `reset_setting` ask it. A reset additionally refuses a key that names a
dict or a list, because a reset is for one setting. Where no default exists, the message says
what actually happened — the key is gone, not restored.

## Test cases

- **TC1 —** reset refuses every key save refuses: a masked leaf, a masked parent, a list,
  `permissions` and a single permission — and writes nothing. (Fails before the fix: each
  deletes.)
- **TC2 —** reset still removes an ordinary override and prunes the emptied parent.
- **TC3 —** reset refuses a key naming a block, even an unmasked one.
- **TC4 —** the message distinguishes "back to the default" from "the key is simply gone".
