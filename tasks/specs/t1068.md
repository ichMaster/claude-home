# t1068 — admin panel, phase 3: the Zirka screen

Phase 3 of `t1037` (`docs/features/ADMIN-PANEL.md`, screen 4). The first phase that writes.

## Problem / goal

The forecast is seventeen model calls and four accumulating stores, and the only way to see
inside it is to read `status/state/mood.log` by hand — a file that is now 1700 lines. When a
reading is wrong, the question is always the same: which stage decided that, and on what
fact. Today answering it means grepping a log over SSH.

The screen also carries the one write that solves a problem which exists right now: a
textarea for pasting a reference. A long reading does not survive Telegram — a long paste
becomes a document, a forward can vanish — and three were lost on 2026-10-31 before this was
understood. A form has no such limit.

## What it is

- **Today's reading** as it was sent, block by block, each with its length against the
  budget from the prompt (300 / 400 / 1800 / 450 / 300).
- **The pipeline** for the chosen day: every logged stage — facts, weighing, draft, review,
  summary, biorhythms — behind a fold, in the order they ran, with the run they belong to.
  A day with several runs (a `--resume`, a recomputation) shows each separately, newest
  first, because "which run produced this" is exactly the question.
- **The computed facts** straight from `astro.py`: the transits with their windows, the
  Moon's events through the day (t1060), the focus and the houses. No model involved, so
  this is the ground truth every claim above rests on.
- **Calibration**: the rules in force with the day each was learned from, and the feedback
  log beside them.
- **References**: the list on file, the ones parked by Zirka's chat and not yet ingested,
  and **a textarea** to paste a new one — with the day, an optional author, and a checkbox
  for distilling rules immediately.
- **Actions**: recompute the day, ask the evening question now, calibrate a chosen day.
- **The chart**: the natal positions, houses with rulers, and the aspects.

## Test cases

- **TC1 — blocks against budgets.** `reading_blocks()` splits a logged summary into its five
  markers and reports each length with its budget and whether it is over. A summary missing
  a block says so rather than silently showing four.
- **TC2 — runs, newest first.** `day_runs()` returns one entry per logged run for a date,
  newest first, each with its stages in logged order; a day with no block yields `[]`.
- **TC3 — parked references.** `parked()` lists what Zirka's chat stored and not yet
  ingested, newest first, with its day and size; an empty directory yields `[]`.
- **TC4 — the write path.** Posting a reference calls `astro_learn.py add --file` with the
  chosen day, and with `--learn` only when asked. The text reaches the file verbatim; an
  empty submission is refused with a message, not stored as an empty reference.
- **TC5 — CSRF.** A POST without the form token issued by this process is refused. Without
  authentication, any page the owner opens on the LAN could otherwise post to this port, and
  these actions start eight-minute pipelines.
- **TC6 — actions.** Each button runs its own script and nothing else; a failure is
  reported, never swallowed into a success page.
- **TC7 — escaping.** The reference text, the log and the feedback are all free text written
  by somebody else (an astrologer's calendar, the owner's own remarks) and are escaped.

## Approach

`panel/zirka.py` holds the collectors, pure over text wherever possible: the log parser
takes the log's text, the block splitter takes a summary string. The screen's own route does
the reading from disk and the running of scripts.

Writes go through the existing scripts — `astro_learn.py add --file`, `mood_feedback.py`,
`mood.py` via `systemd-run` — never by touching the stores directly, so validation stays in
one place and the panel keeps having no store of its own.

**CSRF token**: a random value minted at process start, embedded in every form, required on
every POST. It is not authentication and does not pretend to be; it only stops a page on
another origin from driving the panel, which matters precisely because there is no login.

Out of scope for this phase: the voice test box (it spends ElevenLabs quota, and nothing
depends on it today) and per-stage timings (the log does not record them; adding that means
changing `mood.py`'s logging, which is a different task).
