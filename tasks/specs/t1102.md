# t1102 — panel: phase 10a, configuration as a form and permissions that bind

Phase 10's first half. The owner's order was «потім 10»; phase 11 (the login) is what makes
any of it defensible.

## Problem / goal

Phase 8 made the configuration visible and deliberately wrote nothing. Two different things
were hiding behind the word "rules" there, and they turn out to need opposite treatment:

- **Ordinary settings** — TTLs, counts, windows, times, flags. Changing one is low-stakes and
  reversible, and doing it means editing JSON over SSH today.
- **Permissions** — what I may do without asking. Phase 8's honest finding was that *nothing
  machine-readable exists*: the session runs `--permission-mode auto` with no allow/deny list
  anywhere, and the actual constraints are prose in `CLAUDE.md`. A switch that writes a value
  nothing reads would be decoration — the exact thing I warned about on 2026-10-31.

## What this builds

**A form for ordinary settings.** Every scalar setting is editable; the write goes to
`config.local.json` through the versioned atomic path (so a wrong value is one
`tools/versions.py restore` away), and *Повернути типове* removes the override instead of
writing the default, so the committed default stays authoritative.

Not editable, deliberately:
- **masked keys** (birth data, the calendar id, the owner's name, the voice ids) — they are
  not shown, so they cannot be edited from a page; they stay terminal-only;
- **lists and blocks** — the 603 channels have their own screen, and a textarea full of JSON
  is a way to corrupt a file, not to edit it;
- **`permissions.*`** — see below.

**Permissions that actually bind.** A new `permissions` block in `config.json` with a fixed
set of named decisions, each `free` / `ask` / `never`, plus the three that are not
negotiable. `tools/permissions.py prompt` renders them, `start.sh` appends that to the
system prompt beside the persona and the facts, and the Prompt screen shows it as a part. So
a changed permission reaches the session the same way everything else does, and the restart
banner from t1101 says when it is not in force yet.

**They are set from the terminal, not from the panel** (`tools/permissions.py set <key>
<level>`). This is the owner's standing rule — «дозволи, секрети й токени змінюються ТІЛЬКИ
з терміналу» — and a password on a LAN page is not the same thing as a shell on the machine.
The panel shows them, says where they are set, and offers no switch. Flagged to him for a
decision rather than quietly resolved either way.

## Test cases

- **TC1 —** saving a setting writes it to `config.local.json` and leaves `config.json`
  untouched; the value keeps the type of the default (bool, int, float, string).
- **TC2 —** *Повернути типове* deletes the override and leaves no empty parent blocks.
- **TC3 —** a masked key, a list, a block, and anything under `permissions.` are refused with
  a reason, and nothing is written.
- **TC4 —** a value that will not parse as the default's type is refused before the write.
- **TC5 —** every write takes a version copy first, and a write of an unchanged value does
  not (the dedup from t1080).
- **TC6 —** a key that exists in neither file is refused — the form cannot invent settings.
- **TC7 —** `permissions.py prompt` renders every decision with its level, and `never` lines
  say they are not negotiable; an unknown level in the file renders as `never`, not as free.
- **TC8 —** `permissions.py set` writes the level; an unknown key or level is refused; a
  hard rule cannot be lowered.
- **TC9 —** the permissions block reaches the assembled prompt on the Prompt screen.
