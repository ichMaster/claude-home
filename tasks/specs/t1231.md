# t1231 — config.sh conf() interpolates the key into Python source (code execution)

## Problem / goal

`conf()` in `config.sh` builds the Python one-liner by string-interpolating its argument:
`v = conf('$1')`. A key containing a single quote escapes the string literal and executes
arbitrary Python — and therefore arbitrary shell. Reproduced:

    . ./config.sh && conf "voice.voices.x'); import sys; sys.stderr.write('INJECTED-OK\n'); ('"

prints `INJECTED-OK`. notify.sh passes caller-controlled strings there verbatim
(`--bot` → `conf "telegram.bots.$bot"`, `--voice-as` → `conf "voice.voices.$vname"`), and
the internet-text-exposed headless sessions (digest, social, youtube) are allowlisted for
`Bash(./notify.sh:*)` — so a prompt injection in a mail body or RSS title that talks the
model into a crafted `--bot` value regains full command execution through an explicitly
allowed command, bypassing the t1186/t1207 lockdown.

## Test cases

- **TC1 — regression:** `conf` with a key containing `'); …` executes nothing: the marker
  the payload would print must not appear in stdout/stderr, and the call behaves like a
  lookup of a nonexistent key (empty output). Fails before the change (marker appears).
- **TC2 —** an ordinary key still works: `conf probes.weather.city` returns the same value
  the Python `noosconf.conf` returns.
- **TC3 — edge:** a key with a double quote and backslash is also inert (empty output,
  no error from the Python layer escaping).

## Approach

Pass the key and the repo root to Python as argv (`sys.argv[1]`, `sys.argv[2]`) instead of
interpolating them into the source. No caller changes needed — the function signature is
unchanged. notify.sh-side validation of `$bot`/`$vname` deliberately left out: with argv
passing there is nothing left to inject into, and a bogus name already falls back safely.
