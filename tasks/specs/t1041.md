# t1041 — inbox.py: a failure mid-update re-sends already-sent replies

## Problem / goal

In `status/bots/inbox.py:poll()` only `answer()` is wrapped in try/except. The rest of the
per-update body can raise: `transcribe()` (urllib `URLError`, `subprocess.TimeoutExpired` from
Deepgram), `read_document()`'s `api()` call, `take_reference()` (timeout 600), `run_search()`
(timeout 120), `send()` and `hand_over()` (timeout 300 — `check=False` does not suppress
`TimeoutExpired`). An exception escapes `poll()` before `save_state()` at the end, so neither
the offset nor the `answers` list is committed. Concrete failure: the owner sends text A then
voice B; A is answered and sent, then B's transcription times out — the next `noos-bots.timer`
run two minutes later fetches the same batch and answers A again. A deterministic failure
(a long voice file) loops the duplicate every two minutes, and the hourly cap never
accumulates because `answers` is never persisted.

## Test cases

- **TC1 (regression)** — given two updates where processing the first raises
  (`transcribe` times out) and the second is a plain text message, when `poll()` runs, then it
  does not raise, the second update is answered, and the saved state's offset covers both
  updates (no re-delivery on the next run).
- **TC2** — given a batch where `send()` raises `TimeoutExpired` for the only update, when
  `poll()` runs, then state is still saved with the advanced offset and the failure is logged
  to `dropped.jsonl`.

## Approach

Wrap the per-update body in try/except: a failing update is logged via `log_dropped(bot,
"збій обробки: …", upd)` and skipped, the loop continues, `save_state` at the end always runs.
Trade-off accepted: a transiently-failing message is dropped (and visible in `dropped.jsonl`)
instead of retried — retrying the batch re-sends every reply before the failure point, which
is worse. Out of scope: per-update incremental `save_state`, retry queues.
