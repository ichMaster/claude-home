# t1170 — news probe survives a torn seen-state file and writes it atomically

## Problem / goal

`status/probes/news.py` parses `status/state/news-<topic>.json` at line 26, **outside** the
try block that starts at line 37, and rewrites it on every run with a plain non-atomic
`write_text` (line 78). A power cut or kill mid-write — outages are routine here — leaves
truncated JSON; from then on every run of that topic raises JSONDecodeError before printing
anything, `run.sh` discards stderr and substitutes the generic «Пробник news:<topic> не
відповів», and the topic silently vanishes from digest candidates until someone deletes the
file by hand. youtube.py and watch.py already guard exactly this class (t1044/t1046).

Found by the nightly code review of 2026-11-13 (Medium, confirmed adversarially).

## Test cases

- **TC1 —** given a torn seen file (`{"abc`), the probe still prints valid probe JSON and
  reports the fetched item (regression — crashes before the fix).
- **TC2 —** after the run the seen file is valid JSON again and contains the new item's key.
- **TC3 —** a healthy seen file still filters: an item whose key is already present is not
  reported again.

## Approach

Wrap the seen-file load in try/except falling back to an empty set (losing the seen set only
risks a few repeats; losing the probe loses the topic), and write the file through
`noosconf.atomic_write_text` like the youtube probe does. The lexicographic trim eviction
(Low finding) is out of scope.
