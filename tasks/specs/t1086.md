# t1086 — the Filters screen contradicts the mail probe when mail-rules.json is absent

## Problem / goal

Nightly review 2026-11-01. `panel/sources_screen.py filters()` seeds the mail rules with
empty `шум`/`важливе` lists and merges `status/mail-rules.json` over them; the probe
(`status/probes/mail.py`) seeds with `DEFAULT_RULES` and merges the file over those. The
file is absent on this machine right now, so the probe classifies `invoice`/`рахунок`/`bank`
as важливе (severity warn) and facebookmail as шум — while the panel renders both lists as
«—» and the classify test box answers «звичайне» for the very same messages. A rules file
defining only `шум` misleads the same way for `важливе`. The screen's own docstring says
"as the probes read them", and it does not.

## Test cases

- **TC1 —** given no `status/mail-rules.json`, when `filters()` runs, then the mail rules
  equal the probe's `DEFAULT_RULES`, and `classify("billing@corp.com", "Invoice 42", …)`
  answers важливе — the same verdict the probe gives (regression — fails before the change).
- **TC2 —** given a rules file defining only `шум`, then `важливе` still holds the probe's
  default list (the probe's merge semantics: file keys override, missing keys keep defaults).
- **TC3 — edge:** a present rules file overriding both keys is honoured exactly as before.

## Approach

Import `DEFAULT_RULES` from the mail probe (it is import-safe: `__main__`-guarded) and seed
`mail = dict(DEFAULT_RULES)` before the merge — the same two lines of semantics the probe
uses. No behaviour change when the file defines both keys.
