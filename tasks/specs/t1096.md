# t1096 — panel: the journal pane showed the oldest lines, cut mid-timestamp

Found by the phase-8 review (8c700a3, finding M3).

## Problem

`journal_text` asks `journalctl -n 40` and returns `run_script(...)`, whose last line is
`return ok, said[:600]` — a clamp written for messages that ride a redirect query string.
Applied to a journal it cuts from the **front**, so the pane showed the five oldest lines of
the window and never reached the newest one, with the 600th character landing mid-timestamp
and no sign that anything was cut. Every one of the 14 service panes was exactly 600 bytes,
and `panel.journal_lines` (40), added by the same commit, changed nothing.

The screen's stated purpose is the answer to «чому дайджест мовчав». It was answering with
lines from a run a day and a half earlier.

## Fix

`run_script` takes `cap` and `tail`: the journal asks for `panel.journal_chars` (12000)
characters and keeps the **tail**, with an explicit «… обрізано» marker on the first line
when the cut happened. Every other caller keeps the 600-character head clamp it was written
for, unchanged.

## Test cases

- **TC1 —** a 40-line output returns its **last** lines; the newest line is present.
  (Fails before the fix: the output is the first 600 characters.)
- **TC2 —** `panel.journal_lines` reaches the command, and output longer than 600 characters
  is not clamped to 600.
- **TC3 —** when the cut happens, the text says so; when it does not, no marker is added.
- **TC4 —** `run_script`'s other callers are unaffected: a long output still comes back
  clamped to 600 from the front.

## Approach

The cap belongs to the caller, not to the runner: a task message and a journal page want
opposite ends of the same string. Nothing else about `run_script` changes.
