# t1201 — the watcher runs with no timeout: one wedged probe stops all alerting

## Problem / goal

`status/watch.py` runs `run.sh` (line 60) and `notify.sh` (line 110) through
`subprocess.run` with no `timeout=`, and `noos-watch.service` is `Type=oneshot` with no
`TimeoutStartSec` — which for oneshot means infinity. `services.sh` runs `docker ps` with no
client-side timeout; if dockerd (or the tmux server) wedges, the probe blocks forever, the
oneshot start job never finishes, and `noos-watch.timer` (`OnUnitActiveSec=15min`) never
re-elapses: alarm, loe, auth and services alerting all stop silently until a human kills the
job. Found by the nightly review of 2026-11-18 (High).

A plain `subprocess.run(timeout=…)` would not fix it: on timeout Python kills the direct
child (the shell) and then blocks in `communicate()` waiting for the wedged grandchild
(`docker ps`), which still holds the inherited stdout pipe. The whole process group has to
die before the pipe closes.

## Test cases

- **TC1 — regression:** `run_bounded` on a command whose child outlives the shell
  (`bash -c "sleep 30 & exec sleep 30"`, timeout well under a second) returns `None` within
  a couple of seconds instead of blocking until the grandchild exits. Fails before the
  change: the helper does not exist and the old call would block.
- **TC2 —** a probe run that times out leaves the watcher alive and the state file
  untouched (same contract as empty run.sh output, t1168): `main()` prints a message and
  returns, no signature is wiped.
- **TC3 —** a notify run that times out counts as an undelivered send: the new state is not
  persisted, so the warn retries next run (same contract as a nonzero notify rc, t1046).
- **TC4 —** the happy path still works: probes come back, notify returns 0, state persists
  (covered by the existing tests, re-pointed at the bounded runner).

## Approach

A module-level `run_bounded(cmd, timeout)` built on `Popen(start_new_session=True)`: on
`TimeoutExpired` it SIGKILLs the whole process group, reaps, and returns `None`; otherwise
`(returncode, stdout)`. Both call sites use it; timeouts come from config
(`watch.probe_timeout_sec` 300, `watch.notify_timeout_sec` 180 — well under the 15-minute
tick). The existing watch tests swap their `subprocess.run` fake for a `run_bounded` fake.
Out of scope: `TimeoutStartSec` on the unit (the code bound makes the unit bound redundant),
run.sh's own cache write races (reported as Low).
