# t1064 — panel: unknown push state rendered as «Усе запушено»

Fix from the phase-2 review (`status/state/code-review/2026-10-31-panel-phase2-scan.md`, M2).

## Problem / goal

`git()` returns `""` on any non-zero exit, so `ahead_hashes()` returns the same empty set
for "zero commits ahead" and for "origin/main does not resolve" (fresh clone before fetch,
renamed remote, git failure — `rev-list origin/nonexistent..HEAD` exits 128). The screen
then says «Усе запушено» and marks no commit «локальний» — exactly the claim the
function's docstring promises never to make, on the line the owner uses to decide the
morning push.

## Test cases

- **TC1 (regression)** — when the rev-list subprocess fails (non-zero exit or raises),
  `ahead_hashes()` returns `None`, not an empty set. Fails before the change.
- **TC2** — `render_changes(…, ahead=None, …)` says the state is unknown and does NOT
  contain «Усе запушено»; `ahead=0` still renders «Усе запушено». Fails before the change
  (the old code formats `None` into the warn line).
- **TC3** — `commit_rows(log, ahead=None)` still parses and marks nothing local.

## Approach

`ahead_hashes()` runs its subprocess directly and returns `set[str] | None`, `None`
meaning "could not tell" (non-zero exit, OSError, timeout). `render_changes` takes
`ahead: int | None` and renders a third, honest state. `changes_html` calls
`ahead_hashes()` once and reuses it for both the row marks and the count (it used to run
the subprocess twice per request). Out of scope: catching timeouts inside the generic
`git()` helper (L1 of the scan, Low, left open).
