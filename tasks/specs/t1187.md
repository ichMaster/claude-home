# t1187 — a lost Claude login is reported, not silent

## Problem / goal

On 2026-11-15 the always-on session lost its OAuth login. Telegram messages kept arriving,
but every turn answered `Login expired · Please run /login` in the tmux pane, which the owner
never sees — so for hours he got nothing and did not know why. Nothing watches for this: the
`services` probe only checks that tmux and `claude-home` are alive, and they were.

The same morning the 05:00 restart made it worse: `memory/handoff.py` took whatever
`claude -p` printed as the note, and with the login gone that was
`Failed to authenticate: OAuth session expired and could not be refreshed`. That line was
injected into the next session's system prompt under «Естафета з попередньої сесії», and the
restart was reported as a success «з естафетою».

## Test cases

- **TC1 —** given a captured pane whose latest reply is `● Login expired · Please run /login`,
  the `auth` probe reports `severity: alert`, `value.expired: true`, and a text that names the
  fix (`ssh`, `tmux attach -t claude`, `/login`).
- **TC2 —** given a healthy pane (latest reply is ordinary text or a tool call), the probe is
  `info` and not expired.
- **TC3 — edge:** an old `Login expired` line followed by a newer ordinary reply is healthy; an
  error line followed by `Login successful` is healthy; a reply that merely *talks about*
  «Login expired» mid-sentence is healthy.
- **TC4 — edge:** `Failed to authenticate: OAuth session expired …` printed by the CLI outside
  a reply bullet, and `● API Error: 401 … OAuth …`, are both detected.
- **TC5 —** tmux has no `claude` session → the probe stays `info`/unknown (the `services`
  probe owns that alarm), never a false login alert.
- **TC6 —** the watcher sends the alert once and stays silent on the next tick (its existing
  alert rule: repeated only after `watch.remind_after_sec`), and a probe's `voice` field is
  spoken through `--voice-text` so no Latin script reaches the synthesizer.
- **TC7 — regression:** `handoff.py` given a `claude -p` that prints the auth error (with
  exit code 0 or 1) writes no `handoff.md` and exits non-zero, so `restart-session.sh` keeps
  the conversation instead of pasting the error into the prompt.

## Approach

A new probe `status/probes/auth.py` reads the last `probes.auth.lines` lines of the tmux pane
(`tmux capture-pane`) and looks at the **latest event**: the last reply bullet (`●`), CLI
error line or `Login successful`. Only the latest one counts, so a recovered session goes
green by itself and an old error in the scrollback is not an outage. The patterns live in
`config.json` (`probes.auth`), and the matching lives in `status/tools/authcheck.py`, shared
with the handoff.

Delivery reuses the watcher rather than a new timer: `auth` joins the watcher's default probe
list, so the alert goes out through `notify.sh` (Bot API directly — Claude is the thing that
is down), with voice, once per incident, re-sent every three hours while it lasts, and a ✅
when it clears. The watcher learns one thing: a probe may carry a `voice` field, the Latin-free
copy that is spoken instead of the text.

`handoff.py` refuses a note when `claude -p` failed or when the note is an auth error.

Left out: logging in automatically (needs a browser and the owner), and a faster cadence than
the watcher's 15 minutes.
