# t1178 — inbox history re-expands clamped documents past the argv limit, bot can brick

## Problem / goal

t1176 clamps a forwarded document to `telegram.inbox.max_document_prompt_bytes` (96KB) so
the single `claude -p <prompt>` argv element stays under Linux's 131072-byte
MAX_ARG_STRLEN. But after a successful answer `handle_update` appends the full clamped text
to `st["history"]`, and `build_prompt` re-embeds `history[-8:]` untruncated. The next large
message (or a large `run_search` block) pushes the combined prompt past 131072 bytes, execve
fails with E2BIG, and the answer dies. Worse: two ~60KB documents answered successfully
leave ~125KB of history inside **every** later prompt — every call fails E2BIG, and since
history only rotates on success it never shrinks: the bot is bricked until the state file is
edited by hand.

## Test cases

- **TC1 — regression:** `call_claude` passes the prompt on **stdin**, never as an argv
  element, so no prompt size can raise E2BIG (fails before: the prompt sits in `cmd[2]`).
- **TC2:** a history entry appended by `handle_update` is clipped to
  `telegram.inbox.max_history_entry_bytes` with an explicit truncation marker; short
  entries pass through untouched.
- **TC3 — edge:** clipping cuts on a UTF-8 boundary — a Cyrillic text clipped mid-character
  decodes cleanly, no exception, no mojibake.

## Approach

Two independent layers:
1. `call_claude` sends the prompt via `input=prompt` instead of an argv element (verified
   live: `echo … | claude -p` answers normally with the same flags). This alone removes the
   E2BIG ceiling for any prompt size, including already-oversized state files.
2. A `clip_entry()` helper bounds each stored history entry to
   `telegram.inbox.max_history_entry_bytes` (default 8192) with the marker
   «…(обрізано для історії)», applied where `handle_update` appends — so state files and
   prompts stay sane and an old oversized entry ages out within the normal 12-entry window.

Out of scope: the same argv pattern in `mood_feedback.py` / `astro_learn.py` (reached only
with the already-clamped document, which fits), and retrying failed sends (separate finding).
