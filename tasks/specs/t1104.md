# t1104 — the atomic write tore files under threads, and a lost version was silent

Found by the full review, 2026-11-01 (H1 and M6 in
`status/state/code-review/2026-11-01-panel-full-writes.md`).

## Problem

`noosconf.atomic_write_text` named its temp file `<name>.tmp<pid>`. The panel is a
`ThreadingHTTPServer`, so every request is a thread of **one** process and `os.getpid()` is
the same for all of them: two writes to one target shared one temp path. One thread's write
interleaved with the other's, and one thread's `finally: tmp.unlink()` deleted the other's
temp before its `os.replace`. `os.replace` is atomic; the file it was handed was not.

Measured by the reviewer: a `set_setting` and a `set_channel` started together on a copy of
the real `config.local.json` left it **unparseable in 20 of 40 trials** and raised
`FileNotFoundError` in all 40 — which `rules_action` does not catch, so the owner saw
`500 panel error` over an already-damaged file holding the birth data, the calendar id and
the 603-channel list. Two hundred double-submits of the `CLAUDE.md` editor left **41 files
that were neither version** — body A with body B's tail, longer than either, so the shrink
guard could not catch it. A double-click is enough; nothing disables the button.

Separately (M6): `keep_version` returns `None` on any failure and said nothing, while
`versions.dir` — the setting that breaks it — is editable from the panel's own form. Every
«копію лишилось» message was then a promise nobody kept.

## Fix

- **A unique temp file per write** (`tempfile.mkstemp` in the target's directory), and the
  permissions applied to it before the rename, defaulting to 600 for a new file rather than
  inheriting the umask.
- **`noosconf.locked(target)`** — an `flock` on a sidecar, held across the whole
  read-modify-write — used by every writer of `config.local.json` (both panel screens, the
  permissions CLI, the channel list) and by the file editors. The unique temp stops a torn
  file; the lock is what stops a lost update, and it works between processes too, which
  matters because the timers write these files as well.
- **`version_failed(target)`**: `keep_version` records the failure, and the save messages say
  «копію зберегти не вдалось» instead of implying a copy exists. A lost version still never
  costs the write it was protecting.

## Test cases

- **TC1 —** twenty rounds of two threads writing one file: the content is always exactly one
  of the two bodies, never a weld, and nothing raises. (Fails before the fix.)
- **TC2 —** two threads doing forty read-modify-writes each under `locked()`: both counters
  reach forty — no lost update.
- **TC3 —** two successive writes use two different temp names.
- **TC4 —** when the version copy cannot be taken, `version_failed()` is true and the write
  still lands.
- **TC5 —** the existing torn-write test still proves a crash mid-write cannot touch the
  target (re-hooked at `os.fdopen`, where the temp is written now).
