# t1174 — panel schedule validation rejects dash-leading specs and checks the restart

## Problem / goal

`schedule_action` validates each submitted spec with `systemd-analyze calendar <spec>` with
no `--` separator, so a spec like `--help` is consumed as a flag and exits 0 — it counts as
valid (verified on this host). Submitted beside one real spec, `OnCalendar=--help` is written
into the unit; systemd drops the line with only a journal warning, the unit stays
`LoadState=loaded`, the rollback never fires, and the page reports success while the timer
silently runs a partial schedule. Separately, the exit status of
`systemctl --user restart <unit>` is discarded, so a failed restart after an edit is also
reported as success while the running timer keeps the old schedule.

Found by the nightly code review of 2026-11-13 (Medium, confirmed by execution).

## Test cases

- **TC1 —** a dash-leading spec (`--help` beside a valid one) is refused before the write and
  the unit file is untouched (regression — passed validation before the fix).
- **TC2 —** when `systemctl --user restart` fails, the page says the restart failed instead
  of reporting the new schedule as fully live.
- **TC3 —** the existing good-spec, bad-spec, rollback and unknown-unit tests keep passing.

## Approach

Pass `--` before the spec in the `systemd-analyze calendar` call, so systemd's own parser
judges dash-leading input instead of swallowing it. Capture the restart result and report a
failure in the returned message; the write and the changelog record stand (the file is
correct — only the running timer is stale).
