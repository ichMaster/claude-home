# t1228 — a failed weekly split refuses instead of storing the week as one day

## Problem / goal

`status/astro_learn.py` `split_days()` falls back to `[(first, whole_text)]` when the
model call raises, when the answer is unparseable JSON (silently — no stderr line at
all), or when no block carries a date. `main()` then rewrites `period` to «день» (the
t1223 rule) and stores seven days of the astrologer's windows as one daily record under
the first date, prints an ordinary «записано» and consumes the inbox file. The morning
pipeline reads a week as one day's calendar, and the six other covered days raise
NoCalendar. That contradicts t1223's own commit title: «splits into daily records **or
is refused**».

## Test cases

- **TC1 —** `add --file week.txt --period тиждень --split` with the model call raising:
  SystemExit with a message, nothing stored, the inbox file NOT consumed (regression;
  fails before the fix — it stores and consumes).
- **TC2 —** same with the model answering prose (unparseable): same refusal.
- **TC3 — edge:** `--split` with the default period «день» and a failed call keeps the
  old fallback — the whole text stored under the given day, with the stderr warning —
  because a single-day reference stored whole beats one lost.

## Approach

`split_days()` raises a dedicated `SplitFailed` on its three failure paths (so the
bad-JSON case finally says why). `main()` catches it: for `--period тиждень` it refuses
with `sys.exit` **before** storing or consuming; for any other period it prints the old
warning and stores whole — the pre-t1223 behaviour, which is only poisonous when the
text is a week. Existing split tests updated to the new contract.
