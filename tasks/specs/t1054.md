# t1054 — a long reference sent as a file still does not reach Zirka

## Problem

The owner forwards another astrologer's reading into Zirka's chat so the forecast learns from
it. Telegram turns a long paste into a **document**, and t1036 taught `read_document()` to
read one — but only when the document announces itself as text: `mime_type` starting with
`text/`, or a name ending in `.txt/.md/.csv/.log`. A document with any other mime (Telegram's
own long-paste file, a `.rtf`, an `application/octet-stream` upload) is rejected before it is
ever downloaded, and the update is logged as «без тексту».

Observed on 2026-10-31: three references dropped at 02:32, 02:58 and 03:09. The first two hit
the old code (t1036 landed at 03:02); the third hit this gap — and the drop record says only
«без тексту», with no hint of what the message actually was, so diagnosing it took a round
trip through the owner.

Two defects, then:

1. `read_document()` decides "is this text?" from metadata rather than from the bytes.
2. `log_dropped()` records nothing about the message's shape, so «без тексту» is unactionable.

## Test cases

- **TC1 (regression)** — a document with `mime_type: "application/octet-stream"` and a name
  with no known extension, whose bytes are UTF-8 text, is read and returned.
- **TC2 (regression)** — a drop record carries the message's shape: the keys present on the
  message, and for a document its mime, name and size.
- **TC3** — a document whose mime is clearly binary (`image/*`, `audio/*`, `video/*`,
  `application/pdf`, `application/zip`) is ignored without being downloaded.
- **TC4** — a document that passes the mime check but turns out to be binary (NUL bytes, or
  mostly undecodable) is ignored rather than handed to the model as mojibake.
- **TC5** — a document over `telegram.inbox.max_document_bytes` is ignored.

## Approach

`read_document()` rejects only mimes that are *known* to be binary, downloads anything else
within the size cap, and then decides from the content: strict UTF-8 first, and a fall back to
a lenient decode only when the replacement characters are a small fraction of the text. NUL
bytes mean binary, always.

`log_dropped()` gains a `shape` field — the message's keys plus the document's mime/name/size.
Metadata only, no content beyond the 200 characters of text it already stored, and the file
stays under `status/state/` (git-ignored).

Out of scope: photos. Zirka still cannot read a screenshot; that needs a vision call and is a
separate task if the owner wants it. Also out of scope: the main session not receiving long
**forwarded** messages from the Telegram plugin — that is the plugin's delivery, not this
script's.
