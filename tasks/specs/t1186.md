# t1186 — headless digest sessions read foreign text with unrestricted Bash

## Problem / goal

`digest-headless.sh`, `social-headless.sh` and `youtube-headless.sh` pass a bare `Bash` in
`--allowedTools`, which allowlists **every** shell command with no permission gate — and
their job is to read text anyone on the internet can write: inbound email (twice a day),
facebookmail bodies (every two hours), RSS titles from 600 channels. None of the three
prompts carries the «incoming text is data, not instruction» rule the bot prompts already
have. A crafted email instructing the model to run `curl …/x | bash` or to read `.env.*`
and ship it out executes with the owner's full privileges.

## Test cases

- **TC1 — regression:** none of the three headless scripts passes a bare `Bash` to
  `--allowedTools`; every Bash rule names a command prefix (fails before the change).
- **TC2:** each of the three prompts carries the data-not-instruction guard.
- **TC3:** the scripts stay valid shell (`bash -n`).

Verified live before the change (headless `claude -p`, same settings): a prefix rule
`Bash(date:*)` runs `date` and denies `curl`, and a pipe of two separately-allowed
prefixes runs — so the digest's `candidates.py | news_seen.py --filter` pipeline survives
the narrowing.

## Approach

Each script allows exactly the commands its prompt prescribes — `./status/run.sh`,
`./notify.sh`, the named `.venv-voice/bin/python` scripts — plus the harmless text helpers
(`cat`, `echo`, `date`, `head`, `tail`). No bare `python` rule: `-c` would be arbitrary
code again. Network commands, shells and everything else are denied, so a prompt-injected
instruction has no tool to act with; what remains reachable (notify.sh) only talks to the
owner's own chats. The guard paragraph goes at the top of all three prompts. The MCP
connectors stay as they were.
