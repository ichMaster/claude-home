# t1033 — a reference in Zirka's chat must be split by the model and must recompute the day

## Problem / goal

The owner, twice now (2026-10-30 and again 2026-10-31): a reference forecast dropped into
Zirka's chat should be **read by the model, not parsed by Python**, and taking it in should
**correct and recompute** the day's reading — not quietly file a rule for tomorrow.

Two things stand in the way.

1. **The splitter is a regex.** He sends a week of hourly calendar at once, and
   `astro_learn.split_days()` cuts it into days with `_DAY_HEAD` plus a hand-written month
   table — in Russian and Ukrainian, three-letter prefixes, optional weekday, optional
   bullet. It is exactly the kind of content parsing he has ruled out: a header it has not
   seen (a different bullet, a month spelled out, "сьогодні", a year inline) silently lands
   the whole week under one date, and then day-against-day comparison compares nothing. The
   failure is silent, which is the worst property a parser can have here.
2. **Nothing is recomputed.** `take_reference()` stores the text, distils `ПРАВИЛО:` lines
   and returns them for the reply. The rules reach the weighing, the draft and the summary
   only on the *next* run — tomorrow morning. A reference that arrives today about today
   changes nothing he can see today, which is why it feels like it did not land.

## Test cases

- **TC1 (regression)** — `split_days()` asks the model and returns one block per date from
  its answer; no month table, no header pattern is consulted. With a stubbed call returning
  two dated blocks, both come back with the right dates and bodies.
- **TC2** — when the call fails or answers unusably, the whole text is kept as one block
  under the given date. A reference stored whole beats a reference lost.
- **TC3** — the model's answer is trusted only where it is well-formed: a block with an
  unparseable date is dropped, and if nothing survives the fallback of TC2 applies.
- **TC4** — `take_reference()` triggers a recomputation only when the reference is about
  today; a reference for tomorrow is stored and learned from, and nothing is re-run.
- **TC5** — the recomputation is skipped while another one is already running (a lock), so
  three references pasted in a row do not start three eight-minute pipelines.

## Approach

**Splitting.** `status/mood/split.md` — one cheap call that receives the text and today's
date and answers with a JSON array of `{"day": "YYYY-MM-DD", "text": "…"}`. The model
resolves "Пн 26 октября" against the current year, understands a spelled-out month, a
weekday with no date, "завтра", and a single-day text (one element). Python's only job is
`json.loads` and `date.fromisoformat` — reading the model's structured answer, not reading
the owner's content. The regex, the month table and `import re` go.

**Recomputation.** When the stored reference is for today, `take_reference()` re-runs
`status/mood.py --day <today>` in the background and says so in the reply. A full re-run,
not a `--resume`: the rules feed the weighing and the draft as well as the summary, so
redoing only the last stage would apply a third of what was learned. It costs about eight
minutes and runs detached, so the bot's answer is not held up; the corrected reading arrives
in Zirka's chat the usual way, with the log carrying both blocks for the day (append-only —
the first reading is not erased, it is superseded).

The lock is the systemd unit name itself: `systemd-run --unit=noos-mood-recalc` refuses to
start while one is already running, which is exactly the wanted behaviour and leaves no
stale lock file to clean up.

Out of scope: a cheaper partial recomputation (weighing → draft → review → summary from the
logged facts). Worth doing if eight minutes proves too slow in practice; the facts are
deterministic and already logged, so it is a later optimisation, not a correctness fix.
