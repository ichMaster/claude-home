# t1053 — personal details about the owner leaked into the public repo

## Problem

The repository is public, and the owner's rule is that personal material never enters it
(CLAUDE.md § Git): the committed config holds neutral defaults, `config.local.json` — which is
git-ignored — holds the person. Three tracked files broke that rule. None of them is quoted
here; naming the file and the kind of fact is enough, and repeating the text would publish it
a second time (the first draft of this spec did exactly that, and the commit-time review
caught it).

1. `status/mood.py` — `life_context()` carried a hardcoded fallback that described the
   owner's life in a single line, down to a hobby and his working hours. Dead weight on this
   machine: `astro.context` in the local config always overrode it.
2. `CLAUDE.md` § the morning forecast — one line restated that same life sketch as
   documentation, and the birth-data bullet quoted a historical timezone offset **together
   with the month, the year and the city**, which is a birth date in all but name. The city
   on its own is already public on purpose (the air-raid region and the weather city are in
   the committed config); the date is what must not be.
3. `status/mood/summary.md` — one of the everyday examples given to the writing prompt named
   a specific family relationship. `status/mood/ask.md` already phrased the same idea
   generically, so the disclosure bought nothing.

## Test cases

- **TC1 (regression)** — with nothing configured, `life_context()` returns a short neutral
  instruction, not a description of anybody's life.
- **TC2 (regression)** — no git-tracked file contains any personal value read from
  `config.local.json` (the birth date and its year, the coordinates, the owner's life sketch,
  any subject's life sketch). Fails before the change, passes after. The values come from the
  ignored file at run time, so the test itself publishes nothing.
- **TC3** — with `astro.context` set, `life_context()` returns it unchanged, so the forecast's
  examples keep landing in a real life on this machine.

## Approach

`life_context()` loses the hardcoded life and falls back to the same neutral instruction a
named subject without a `context` already got; the two branches collapse into one lookup. The
documentation spots are reworded to describe the *mechanism* — a life sketch comes from the
local config and is handed to the prompts at run time — instead of its content. The example
in the writing prompt is generalised to match the one in `ask.md`. Nothing changes at run
time: the values in use come from `config.local.json`, verified for the owner and for the one
configured subject.

Deliberately out of scope:

- **Rewriting git history.** The lines are already pushed; a force-push over 25 commits to
  erase a handful of ordinary words costs more than it buys. Offered to the owner separately —
  his call, not mine.
- **Generic example strings elsewhere** (a weekend chore used as a CLI example in
  `tasks/store.py`, the same chore in the admin-panel sketch). They illustrate a command;
  they do not state facts about him.
