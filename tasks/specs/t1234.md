# t1234 — a failed changes.py run exits 0 silently; the 23:30 summary disappears

## Problem / goal

`status/changes-send.sh` runs without `set -e` and never checks the collector
pipeline's status: when `status/probes/changes.py` exits non-zero or prints non-JSON
(a venv problem, a corrupt changelog line, disk full), `$body` is empty and the
`[ -z "$body" ] && exit 0` line treats the crash exactly like a legitimately quiet
day. `noos-changes.timer` records SUCCESS, no Telegram message goes out, nothing in
systemctl distinguishes the two — the same failure shape that cost eight silent nights
before code-review-headless.sh got its explicit missing-report check.

## Test cases

(The script runs against a fake `$HOME` — a copy of changes-send.sh, a stub venv
python, a stub probe and a stub notify.sh that logs its argv — nothing real is sent.)

- **TC1 — regression:** changes.py exits non-zero → notify.sh is called with a ⚠️
  warning and the script exits 1. Fails before the change (silent exit 0).
- **TC2 — regression:** changes.py prints non-JSON → the same warning path, exit 1.
- **TC3 —** changes.py prints `{"text": "щось"}` → `📝 щось` is sent, exit 0.
- **TC4 — edge:** `{"text": ""}` → nothing sent, exit 0 (a genuinely quiet day stays
  quiet).

## Approach

Run the two stages separately and check each: a failed collector or a failed parse
sends one quiet ⚠️ line through notify.sh and exits 1, so the timer records the
failure and the owner hears about it once. Only a successful parse with empty text
keeps the silent exit 0.
